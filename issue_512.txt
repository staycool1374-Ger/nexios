### Domain / Subsystem

scheduler

### Summary

Because NexIOS is a hard real-time operating system (RTOS) designed for deterministic safety, stripping the kernel down to just four primitives (Scheduler, IPC, Page Tables, Interrupt Routing) introduces four massive engineering bottlenecks and architectural caveats:

[1](https://nexios-2.jimdosite.com/). The IPC Performance Chasm (The Context-Switch Tax)

• The Caveat: In the hybrid model, if an application requests a file, it drops into the kernel, the VFS reads the disk, and it returns. In v0.6.1, a file request requires a multi-step game of telephone: App \(\rightarrow \) Kernel \(\rightarrow \) VFS Server \(\rightarrow \) Kernel \(\rightarrow \) Disk Driver \(\rightarrow \) Kernel \(\rightarrow \) VFS Server \(\rightarrow \) Kernel \(\rightarrow \) App.
• The Risk: This explosion of context switches can utterly destroy throughput. If the IPC Fastpath (#398) isn't flawlessly optimized at the assembly/CPU register layer, the time spent swapping CPU state (TLB flushes, page table switches) will bottleneck the entire system, violating real-time guarantees.

2. High-Frequency Interrupt Starvation (The Multiplex Lockup)

• The Caveat: Issue #[1](https://nexios-2.jimdosite.com/)92 forces all hardware signals out of the kernel into a Userspace IRQ Multiplex Server. Instead of the CPU instantly executioning a hardware interrupt handler in Ring 0, the kernel must catch the interrupt, translate it into an IPC message, wake up the IRQ Server, map the privilege, and let the user-space driver process it.
• The Risk: If a high-frequency device (like a network card or high-rate sensor) floods the system with interrupts, the Userspace IRQ Server can become a bottleneck. It risks dropping interrupts or "starving" other lower-priority background tasks because it spends 100% of its time processing IPC wakeups.

3. Priority Inversion & Context-Donation Deadlocks

• The Caveat: To fix the performance issue above, Issue #190 introduces Scheduling-Context Donation. This allows a high-priority, real-time application to "lend" its CPU priority and time slice to a passive user-space server (like the VFS) so the server can finish the request quickly.
• The Risk: This creates a web of dynamic priority adjustments. If Server A (handling a real-time task) calls Server B, which calls Server C, a single logical bug in the donation chain can cause a Priority Inversion Deadlock. A low-priority background logging task could accidentally block a critical real-time motor control task because a server context didn't bubble back down properly.

4. Dynamic Memory Paradox (Kernel Never Allocates)

• The Caveat: Issue #193 mandates a Userspace Frame/Region Manager, declaring that "the kernel never allocates memory." The kernel can no longer dynamically create memory structures for its own internal tracking; it must request pages from a user-space server.
• The Risk: This creates a classic chicken-and-egg paradox. If the kernel needs memory to process an IPC message sent by the memory manager itself, it can easily lock up. The code must rely entirely on incredibly strict, pre-allocated static memory pools (RAII compile-time guards with zero-heap allocations). If a pool is sized incorrectly by even a few bytes, the system will face memory starvation with zero ability to adapt on the fly.

These problems need to be addressed in several issues and their specifications and foundations need to be fixed before real transitioning can take place.

Goal of this task is a complete and human comprehensible specification and plan to move from actual hybrid-kernel into a microkernel addressing al actual issues bounded in milestone v0.6.1 giving a complete overview of all system parts with
their interactions and contracts.
