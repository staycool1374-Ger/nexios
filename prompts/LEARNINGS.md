### #10 — MSI-X Vector Infrastructure: per-vector caps + capability-backed delivery (2026-09-02)
- **Learned:** (1) MSI-X shares the IrqDelivery table with PIC IrqCaps — the window widening to 33–255 MUST keep every kernel-reserved vector inside it excluded (audit iter-1 S1): vector 64 is the xAPIC scheduler timer (`arch::APIC::APIC_TIMER_VECTOR`, drives the tick when `CONFIG_USE_APIC_TIMER=1`) and 0xFF is the APIC spurious vector. An armed slot at 64 makes `isr_entry(64)` swallow every tick (EOI + early return before `Scheduler::on_tick`) = total scheduler starvation. Exclude in BOTH `pci_alloc_vector` (reserve in `init_vector_alloc`) AND `claim_slot` (defense in depth — a hand-crafted vector never sourced from the allocator cannot claim a kernel slot). (2) One MSI-X table entry programs exactly ONE vector: single-owner must be per-(BDF,entry), not per-vector — two caps on the same entry each get a DIFFERENT vector (from `pci_alloc_vector`), and the second create would reprogram the shared table slot and hijack the first owner's delivery. A small static claim registry (bounded by CONFIG_CAP_MAX_MSIX) + snapshot_reset closes it. (3) The MSI-X table is device MMIO (e.g. 0x81040000), NOT PMM — `VMM::map_page(HHDM_OFFSET+page)` is the only legal access (no raw `reinterpret_cast<volatile uint32_t*>(phys)`); map page-floor→page-ceil so a 16-byte entry never straddles an unmapped page. The PT page allocated by a test-time `map_page` is reclaimed by the HHDM PD-restore AFTER the ResourceTracker check → spurious +1 PMM leak warning; the fix is the iommu probe-once pattern — pre-map MSI-X tables at boot (`pci_scan_all` → `pci_msix_premap_all` + cached `table_kva`) so test-time creates reuse the cached KVA (ResourceTracker-clean). (4) `pci_find_capability` on a phantom BDF (255:31.7) loops forever: config reads return 0xFF/0xFFFF, STATUS fakes CAP_LIST, CAP_PTR=0xFF, and `readb(0xFF+1)` truncates to `readb(0x00)`=0xFF → unbounded. Reject `pci_device_exists` first + bound the walk (256 steps) — CODING_STYLE §6. (5) **Release-only boot regression (the hardest):** adding `.bss` (g_msix_cache[128], g_entry_claims) grows the kernel's load footprint → GRUB places its Multiboot2 info ABOVE the kernel image, and with the bigger kernel it lands just ABOVE the PMM reserved end (~0x7BC000) → in the PMM free range → an early allocation overwrote `total_size` (read 21) → `mb2_find_tag(8)` found no framebuffer tag → `Framebuffer::available()` false → `Terminal::instance_` null → release-only `shell_tasks_memory_columns` failed (empty capture) while DEBUG passed. Symptom looked like a Terminal/capture bug; root cause was GRUB-info placement vs PMM. Fix: reserve the multiboot info range in PMM (`PMM::reserve_range`) right after `PMM::init`, gated on magic==0x36D76289. Diagnosing: `Logger::info` does NOT support `%p` (prints literal) — use `0x%llx` with `(unsigned long long)(uintptr_t)`.

### #9 — IOMMU DMA Protection Layer: live VT-d enablement (DMAR discovery, register programming, QI flush) (2026-09-01)
- **Learned:** (1) Issue #9 was the phase-2 DELTA on the closed #4 software-only IoMmuManager — live VT-d on QEMU. The kernel's ISO is UEFI-only El Torito: SeaBIOS CANNOT read it under `-machine q35` ("Could not read from CDROM"), so the live-variant QEMU flags MUST boot via OVMF/UEFI (`-drive if=pflash,...,file=edk2-x86_64-code.fd`). Also the FAT32 IDE drive (`if=ide`) is lost under q35 (SATA-only) — the iommu_live test class must be disk-free. (2) QEMU's intel-iommu is a "dynamic sysbus device" — it CANNOT be attached to the default `pc` machine, only q35. (3) QEMU/Linux register map differs from naive spec reading: VER=0x0, CAP=0x8, ECAP=0x10, GCMD=0x18, GSTS=0x1c, RTADDR=0x20, FSTS=0x34, FECTL=0x38, IQH=0x80, IQT=0x88, IQA=0x90. My first attempt used the wrong offsets and SRTP never landed — register-fidelity against the actual emulation (or Linux intel-iommu.h) is the fastest debugging path, not the spec's mental model. (4) The QI descriptor encoding: type field is low nibble (CTX=0x1, IOTLB=0x2) and the GLOBAL granule is bits 4:5 (`1<<4`), NOT bit 31 IV + bits 11:8 — a Linux/QEMU convention. IQT/IQH hold the byte offset >> 4 (index<<4 in the register). (5) The context-entry Translation Type (TT, bits 3:2) is a TWO-BIT field per spec §9.3: TT=00b translate-through-ASR, TT=10b pass-through. The issue-#4 code treated bit 2 as a single "translate" flag — that made the live passthrough entry (Present, bit-2 clear) an actual TRANSLATE entry with NULL ASR (device would walk PA 0), and a user attach with bit-2 set was TT=01b Device-TLB (rejected when DT unsupported). SIL-audit-iter-2 S1 caught it; the cap_iommu tests could not (they assert ASR, not TT). (6) ACPI tables under QEMU sit near the top of RAM (~251 MiB), ABOVE the boot's 128 MiB identity map — every accessed table page must be mapped on demand via VMM::map_page(HHDM_OFFSET+phys,...). (7) probe_hardware() must CACHE its result: test isolation rewinds low memory between tests, so a re-probe would dereference a stale multiboot2 info pointer (page fault in mb2_find_tag). g_mmio_base is a pure hardware fact (persists across force_present(false)); only g_live/g_translation_live are the software authority that force_present clears — so the cached re-probe can restore live state and enable_translation can retry. (8) The iommu_live class must NOT be added to register_all_tests() — it fails on the default pc build (no DMAR); it lives only in the class table + a Makefile CLASS=iommu_live variant.

### #8 — Fine-Grained Hardware I/O Delegation: user MMIO map syscalls + IOPB revocation closure (2026-09-01)
- **Learned:** (1) Issue #8 was a DELTA on the closed #3 MmioCap/IOPB work: a capability-gated user-MMIO map syscall surface (`SYS_MMIO_MAP`/`SYS_MMIO_UNMAP`) and the closure of the #3 revocation gap (retroactive IOPB bit clearing) — the milestone umbrella needs BOTH pieces, not a new abstraction. The user-MMIO registry is a static bounded table keyed by owner_task_id+gen (IrqDelivery pattern) — never a new TCB field (the 4-memset-site sentinel gotcha). (2) A device BAR phys is NOT a PMM page: `map_page_in_pml4(user=true)` ENSUREs `PMM::is_user_page`, so a direct user map panics. The principled fix scopes the ENSURE to `phys_addr < PMM::total_memory()` — kernel RAM stays guarded, device phys (>= total RAM, PCI MMIO hole) maps user-accessible. The auditor approved this as the correct semantics, not a Heisenbug mask. (3) A stored PML4 in any registry MUST be drained before the PML4 is freed on EVERY path that swaps it — `exec_into_current` (exec) AND `TaskControlBlock::cleanup` (the iter-2/iter-3 S1s). An exec swaps+frees the old PML4 without going through cleanup, so a registry keyed to a stored pml4 dangles across exec; and cleanup frees the PML4 before `release_all_objects`/object-list teardown, so the drain must run INSIDE the `if (page_table_)` block BEFORE `free_user_pages`. (4) Fork deep-copy of a user MMIO-window PTE memcpys `HHDM+device_phys` — device phys is outside the direct map → user-triggerable kernel #PF (panic), AND the child would inherit device access without a capability (contract violation). `deep_copy_user_pages` must SKIP leaf frames failing `PMM::is_user_page` at ALL leaf sites (x86_64/aarch64 PT + both riscv64 sites), leaving the child's window unmapped (fail-closed). (5) A registry/ledger that dereferences a capability (e.g. `mmio->size` in the unmap path) must hold a reference for the slot lifetime: per-slot `acquire()` pin, released OUTSIDE the lock (the last release runs dispose → MemPool::free → re-entrant `invalidate_cap` → s_lock_). And the pin must be released only by the path that observes the occupied true→false transition — a concurrent cross-task revoke clearing the slot during the unlocked VMM window makes an unconditional `release()` a double-release (iter-5 S2). Re-validate `occupied && mmio && va [&& owner/gen]` at the clear step. (6) Tests: fixture tasks with a user PML4 must be `create_user`-based (real `page_table_`); a kernel-created task's `page_table_` is 0 and map() fails. Device-like phys for fork tests must be a REAL non-RAM address (>= total_memory), not a user PMM page — a user page is legitimately deep-copied. Test isolation rewinds PMM between tests, so a cached `g_dev_phys` in a static global is stale by the next test — allocate per-test. (7) Cross-task test races: set the harness-signal flag ONLY after the operation that gate depends on (grant installed), never before — the auditor flagged a pre-grant signal as a Heisenbug (timer preemption lets the harness assert on not-yet-installed state).

### #7 — User-Space IRQ Delivery System: NOTIFY-mode capability-backed IPC bridge (2026-09-01)
- **Learned:** (1) The IRQ→IPC notification bridge (issue #7) is a DELTA on the closed #2 delivery table, not new syscalls: reuse `IrqDelivery` slots and add a per-slot `IrqDeliveryMode{WAIT,NOTIFY}` bound atomically at arm() under the slot lock. The mode must be read/written ONLY inside that lock scope (same check-then-act TOCTOU discipline as #2's owner revalidation). (2) Auditor S2: a user-controlled uint64 syscall arg must be validated RAW (`arg1 != 0 && arg1 != 1`) BEFORE the narrowing `static_cast<IrqDeliveryMode>` — otherwise 0x101→NOTIFY and 0x100→WAIT wrap into valid modes and defeat the "unknown modes fail closed" contract; probe the wrapping value (0x101) in a test, not just an obviously-invalid 2/0xFF. (3) `Notify::wait()` is NOT a spinning block like sys_irq_wait: it sets BLOCKED + arms a deferred reschedule and RETURNS immediately — the switch only applies on the next timer tick. A test worker that assumes wait() blocks runs to termination before the harness can wake it (test hung; harness gate `task_blocked` never observed BLOCKED). Fix: mirror sys_irq_wait's explicit `while (state == BLOCKED) arch::pause()` spin AFTER wait() returns, then RE-READ the delivered value via `notify.try_wait()` (wait() may have returned a stale 0 when the ISR delivered while descheduled). (4) In release_slot_idx/drain_task the wake target fields (`recipient`/`recipient_gen`) must be captured BEFORE clearing them — clearing first silently nulls the notify target and leaves the driver BLOCKED forever (the hang was a wake-ordering bug, not a lock issue). (5) drain_task ordering trap: `TaskControlBlock::cleanup()` destroys `~Notify` (task.cpp:1857) BEFORE `IrqDelivery::drain_task` (task.cpp:1870) — draining a NOTIFY slot whose recipient is the dying task must NEVER call notify() on the destroyed object (UAF); the wakers-own-wakeup contract does not apply to an already-TERMINATED task. (6) The revoked sentinel for NOTIFY mode is 0 (`sync::NOTIFY_INVALID`): it wakes a BLOCKED waiter but is invisible to polling `try_wait()` (which only consumes non-zero values) — document this asymmetry in the spec so polling drivers don't rely on observing revocation. (7) EventGroup mode was DEFERRED (scope decision posted on the issue): EventGroup has no value/error channel, its multi-waiter model mismatches the single-recipient slot, and the revoke-wake contract would need a documented bit protocol.

### #103 — aarch64 deep_copy_user_pages invalid L3 table descriptors (2026-09-01)
- **Learned:** (1) On aarch64 stage-1 the descriptor-encoding rules differ by LEVEL: block descriptors (L1/L2) are bits[1:0]=01, PAGE descriptors (L3) are bits[1:0]=11, and TABLE descriptors (L0/L1/L2 next-level pointers) are ALSO bits[1:0]=11 — a table pointer built as `PAGE_PRESENT|PAGE_WRITE|PAGE_USER` (x86 idiom) collapses to bits[1:0]=01 on aarch64 (PAGE_WRITE=0, PAGE_USER=1<<6) and is a reserved/invalid encoding: every MMU walk of the space translation-faults. `#if CONFIG_ARCH_AARCH64` guards that emit `PAGE_PRESENT|PAGE_TABLE` at table-pointer sites are mandatory; the x86 arm stays byte-identical. (2) AF (bit 10) and AttrIndx (bits[4:2]) are RES0/IGNORED in stage-1 TABLE descriptors — the minimal table-pointer form is `PRESENT|TABLE`; the L3 LEAF carries AF/AttrIndx (set by map_page / inherited by deep-copy verbatim flags). Mirror the e24b1415 table sites, not the leaf sites. (3) When a mid-test `JARVIS_ASSERT` aborts, teardown does NOT run → the harness reports `LEAK: PMM +N`; that's a symptom (assertion too late/loose), not a real leak — put teardown-correctness checks in a state that completes. (4) Leaf-frame extraction must use the arch 48-bit frame mask (`0x0000FFFFFFFFF000`), never `~0xFFF` — user leaves carry UXN(54)/PXN(53) and `~0xFFF` leaks them into the "phys" (same class as the #100 DESC_PHYS_MASK defect). (5) Userspace probes with arch-specific inline asm (ud2/divq) compiled via the `userspace/%.c.elf` pattern rule for EVERY arch silently break the aarch64/riscv64 build — guard probe bodies with `#if defined(__x86_64__)` (inert elsewhere; the loading tests are x86-guarded). The #91 x86-only probes went unnoticed because #91 never built a cross-arch target; cross-arch builds are the regression net. (6) An ISSUE-level "smoke test when runtime resumes" requirement can outscope the deterministic fix gate: the EL0 fork smoke test depends on unexercised aarch64 scheduler/process infrastructure — defer to a follow-up issue (#104) rather than balloon the gate, and make the smoke test assert a POSITIVE child-execution marker (a translation-faulted child also terminates).

### #91 — ISR_NOERR misclassification: #VE(21)/#HV(28) push error codes (2026-08-31)
- **Learned:** (1) Per-vector error-code classification is a real correctness hazard, not style: on modern CPUs vec 21 (#VE Intel VMX / #CP AMD CET) and 28 (#HV) DO push an error code. Declared ISR_NOERR, the CPU-pushed error code is consumed as the first GPR (RAX) by isr_common, so the C dispatcher reads garbage, and iretq pops a misaligned frame ⇒ triple-fault-class on any host that raises them (latent on QEMU without nested virt). A macro-level `%assign` frame audit pins BOTH stub classes to the same 16-byte frame (NOERR = synthetic 0 + vec; ERR = 8-byte CPU code + vec) and makes any drift a build failure — but it can NOT catch a silent classification swap (identical frame sizes), so the exported `__isr_vectors_err_mask` + a mask-equality test is the regression gate, and it must live in the `all` gate (auditor S3). (2) A reserved-vector fail-stop policy (15, 22-26, 29, 31 → panic, not user-mode SIGSYS) is a deliberate fault-isolation→fail-stop shift the auditor must flag; it is safe here because no normal hardware raises those vectors, and the branch sits after the `g_user_access_recover_ip` redirect so safe_copy recovery still wins inside the copy window. (3) Weak-hook test seams: a `__attribute__((weak))` no-op production hook overridden by a strong test symbol (the stack_overflow_hook pattern) gives a deterministic dispatch probe with EXACT production parity when unarmed; the armed-latch must be confined to `arch::IrqGuard` scopes so a real timer IRQ can never be swallowed (residual NMI hole is theoretical + self-detecting). (4) Compiler folding defeats fault-probes: `1UL / runtime_value` is rewritten by GCC into a compare (`1/x == (x==1)`) with NO division instruction — a real `#DE`/`#UD` probe must use inline asm (`ud2`; `divq %rcx` with zero divisor). ### #101 — Hard RT measurement under QEMU (2026-09-03)
- **Learned:** (1) GNU Make `$(if ...)` SPLITS function args on commas — `$(if $(filter $(CLASS),x),-icount shift=0,sleep=off,)` becomes three args and leaks `sleep=off,` into the QEMU command line ("Could not open 'sleep=off,'"). Fix: pre-expand comma-bearing flag strings into a variable and reference the variable inside the `$(if)`. (2) QEMU 11 `-icount shift=0,sleep=off` is INCOMPATIBLE with this kernel: the APIC TSC-deadline path (`wrmsr(MSR_TSC_DEADLINE, rdtsc()+delta)` in apic.cpp) reads the virtual clock from a non-IO TB → QEMU-side "Bad icount read" (cpu_exec.c can_do_io guard). With `-cpu max` removed (periodic APIC) it boots but stalls at the daemon-ready handshake under icount. icount stays opt-in (`HRT_ICOUNT=1`) for QEMU versions that fix the interaction. (3) TCG rdtsc advances in COARSE QUANTA: only ~30/2000 back-to-back rdtsc deltas are non-zero (avg ~1050, max ~3000). Latency asserts must not demand every sample non-zero — use ">=1 non-zero + magnitude sanity" canaries. (4) A send_sync roundtrip under TCG spans MANY ticks (base avg ~3.0M cycles, p95 ~2.1M, max ~4.8M) — the issue's illustrative 1500-cycle bound is far below reality; bounds must be calibration-derived with headroom (stress ≤ base×8, wedge cap 20M ≈ 4× observed base max). (5) The test registry is a fixed array `MAX_TESTS = 1024` (test.hpp) — registering past it logs "Test registry full" and silently DROPS the test; the debug all gate still passes but TCOUNT shows expected>actual. Bump MAX_TESTS when growing `all`.

### #102 — Scheduler tests with hard-RT time assertions (2026-09-03)
- **Learned:** (1) A task `hlt`-spinning in a non-blocking `IPC::recv` stays READY and STARVES all lower-priority tasks — you cannot measure wake latency with a high-prio spinning receiver; the woken task must GENUINELY block (Semaphore::wait per the sync pattern = BLOCKED + dequeue_ready) and the measurer must sit ABOVE the prio-10 harness (else the harness preempts it). (2) IPC wake is best measured via `send_sync` roundtrip (the measurer genuinely blocks → the receiver dispatches → replies → measurer resumes) — this IS the real deferred-switch IPC wake path. (3) New test-source files are picked up by the auto-glob, but the GENERATED per-file rules (`mk/cpp-rules.$(ARCH).gen.mk`) only regenerate when rules.mk/Makefile change — a new .cpp needs `rm -f mk/cpp-rules.x86_64.gen.mk` or make errors "No rule to make target". (4) The registry capacity SILENTLY DROPS tests past MAX_TESTS: the #101 gate already dropped 2 (log: "Test registry full (1026)" ×2) yet still showed a clean TCOUNT=1026 match — the true `all` count must be measured from a run with generous capacity, not assumed. Bumped MAX_TESTS 1032→1056 and set all=1035 from the measured TCOUNT. (5) Prio placement rule for latency tests: measurer > harness(10) AND woken > measurer, so the wake tick preempts correctly; the hammerer stays below everything (prio 1).

### #92 — Syscall tiered FAST/FULL dispatch (2026-09-03)
- **Learned:** (1) A constexpr static member initializer in a class CANNOT reference a member function declared LATER in the class body (clangd "undefined function in constant expression") — the builder must be a namespace-scope free function (syscall_fast_mask_from) declared before the class, and the array (k_syscall_fast[]) must also precede the mask. (2) The issue's literal FAST list was not implementable: SEND/RECEIVE/SEND_SYNC deref user buffers (checked_ptr / safe_copy_to_user in syscall_handlers_ipc.cpp) so a canary-skip would be a privilege-escalation hole, and NANOSLEEP does not exist in SyscallNumber — the audited pointer-free set is {YIELD, GET_TICKS, PRINT, CREATE_MAILBOX, DESTROY_MAILBOX, GETPID, PAUSE, REBOOT, HALT}. (3) Relocating the canary check into scheduler hooks (context-switch + tick) creates an EXEC-WINDOW false-trip: exec_into_current swaps page_table_ to the new pml4 before install_segment_canaries arms the new canaries — a sample landing in between walks STALE canary VAs against the new pml4 (virt_to_phys → 0) → spurious panic. Fix: clear canary_installed=0 before the swap (verify no-ops), install re-ORs. The auditor caught this (S2) — a hot-path canary hook must be audited against every page_table_ transition. (4) `handle_fast` in tests cannot call PAUSE/HALT/REBOOT — they halt the CPU and never return; the call-correctness test must skip them (membership is still verified by the mask test). (5) The live syscall entry is `int $0x80` → C ISR → Syscall::handle, so the paper's 'asm bitmask test' lands in C, not the dead syscall_entry.asm.
