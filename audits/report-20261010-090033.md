## Root cause (verified independently)

`FrameUserMap::snapshot_reset()` (and the `MmioUserMap` / `PagerRegistry`
equivalents) release the `KernelObject` pins held by their registry slots. These
calls ran AFTER `MemPool::restore_pool_data()`, which byte-rewinds pool block
data — including each object's inline `ref_count_` — to the snapshot baseline.
Baseline `B=1` for the daemon's CSpace frame slot (the daemon maps lazily, so no
pin exists at snapshot time). During a test the live count is `L=2`
(slot + map pin). Restore order (old): MemPool rewind sets `1`, then pin release
→ `0` → `dispose()` frees the `FrameCap` block (debug poison `0xDD`) while the
restored CSpace slot still points at it → next `SYS_FRAME_MAP` → `cap::lookup`
finds the slot occupied/gen-matched but `slot.obj->acquire()` reads poison →
fails → `RAMDISK_ERR_NOMEM`. Fix: release pins first (`L→L-1=B`), then rewind to
`B`. `KernelObject::release()` disposes on the 1→0 transition
(`kernel_object.hpp:96-100`) and `ref_count_` lives inside the MemPool block, so
the mechanism is real and the live-first reorder is correct.

## FINDINGS

- [S3] `src/kernel/test/test_isolate.cpp:1058-1073` — correctness of the move
  rests on an unstated invariant: the pin-holding registries
  (FrameUserMap/MmioUserMap/PagerRegistry) are EMPTY at every snapshot
  (re)capture. WHY: the new order is release-pin-then-rewind; if a registry pin
  were already present at capture time, `B` would include it and the rewind
  would re-inflate refcount by one (a permanent block leak). Verified it does
  hold: `snapshot_create()` runs at suite start (`src/lib/test.cpp:401`) before
  any `sys_frame_map` (only caller `syscall_handlers_shm.cpp:103`) and the
  daemon maps lazily; the later unconditional pool recapture
  (`test_isolate.cpp:1720`) always runs after the 1071 reset within the same
  cycle; `reload_daemon_tasks()` (1866-1873), `vfs::reset_and_remount()` and
  `vfs::tmpfs_reset_root()` create no registry pins. Recommend anchoring the
  invariant next to `snapshot_create`.
- [S3] `src/kernel/test/test_isolate.cpp:1071-1073` — arch-neutral move changes
  non-x86 behavior. WHY: the three calls were previously inside
  `#if defined(CONFIG_ARCH_X86_64)` (old site ~1662-1684); on aarch64/riscv64
  they now run for the first time. Correct-by-design (registries are
  arch-neutral; includes at 55-60 unconditional) but unexercised by this
  x86-only campaign.
- [S3] `src/kernel/cap/frame_map.cpp:289-306` / `mmio.cpp:330-344` /
  `pager_registry.cpp:413-430` — detector coverage gap on already-freed blocks.
  WHY: for a cap whose MemPool block is already freed+0xDD-poisoned,
  `refcount()` reads `0xDDDDDDDD` (>1) and the detector stays silent;
  acceptable because the #320 baseline-cap case legitimately reads 1 and does
  fire (confirmed by the single PRE-FIX fire), and the detector is a
  diagnostic, not a correctness gate.
- [S3] `src/kernel/test/test_ramdisk_fs.cpp:98` — the patch carries the entire
  276-line test file as a new blob; only the double-unlink assertion is
  #320-relevant. WHY: the file is untracked in HEAD, so `git diff HEAD` renders
  it whole; its build/registry wiring (`test_registry.cpp`, `mk/*.gen.mk`) and
  the `storage 154→160` expected-count bump live outside this patch (#314

- [S3] `src/kernel/test/test_expected_counts.hpp:281` — `capability` expected
