MEASURED FINDINGS THAT SHAPE THE CHANGE (establish, do not assume)
- F1. The counter is .bss-zeroed on every arch (global_state.cpp:124). SBI ecalls from S-mode trap to M-mode (mtvec), never through the kernel stvec, so they cannot increment it; S-ecall delegation (medeleg[9]) is not part of the boot contract — and the pinning read itself is DEREGISTERED (test_riscv64.cpp:1423-1426: medeleg is an M-mode-only CSR, illegal-insn in S-mode), so the premise holds a fortiori: S-mode cannot even observe medeleg, and either delegation outcome leaves no residual (M-mode handling never enters stvec; delegated S-ecalls pair the entry inc with the tail dec). Therefore "after the last SBI call" is NOT the fix point — the only increment site is syscall_entry.S:160, reached only once stvec is live and only while SIE==1 (or on an exception). At handover the count must read 0; whether the observed 4 is present AT handover or accrues AFTER it is exactly what step 13 measures.
- F2. The only non-decrementing trap path is .Ltrap_park (syscall_entry.S:546-555), which halts forever and therefore cannot accrue in a boot that completes. The remaining accrual candidate is frame abandonment across an apply (documented as accounting-sound at syscall_entry.S:219-238) — i.e. a genuine balance bug, not a firmware artifact.
- F3. On aarch64 the trap vector never touches the counter (grep "nesting" in arch/aarch64 → comments + the dead PerCpu.isr_nesting_depth field only). The effective counter (isr_nesting_own() → plain global) is permanently 0, so the aa64 baseline is 0 trivially, not by construction. Record as S2 finding; do not fix here (that is an aarch64 behavior change needing its own audit).
- F4. PerCpu.isr_nesting_depth (0x20) exists on all three arches but is authoritative ONLY on x86_64 (gs-relative RMW in isr_stubs.asm). On rv64/aa64 it is layout-only (percpu_init_bsp zeroes it, nobody reads it). A future "normalize the per-CPU field" fix would be a silent no-op on rv64 — the doc blocks must say so.

## INVARIANTS & CONCURRENCY BOUNDARIES
- INV-NEST-1 (#514, scheduler_snapshot.cpp:224-228): the counter counts OUTSTANDING TRAP FRAMES; a write between a frame's entry-inc and exit-dec corrupts the balance. The handover write is legal only where zero frames are outstanding: SIE==0, single-threaded, pre-scheduler, before the first S-mode trap can complete — exactly the post-percpu_init_bsp point in higherhalf_entry. The normalizer asserts it (ENSURE(!arch::interrupts_enabled())) instead of trusting the caller.
- INV-NEST-2: exactly one writer, one-shot BY CONSTRUCTION (single call site, step 8). WriteClass::BOOT_ONLY rejects any post-boot write (returns false, DEBUG audit-ring entry) but does NOT count writes — a second BOOT-phase write would succeed (verify_and_write gates phase only, global_state.hpp:130-133); no second call site exists. Debug and release follow the same control flow (no CONFIG_DEBUG divergence).
- INV-NEST-3: no lock, no allocation, no RT-path cost — one aligned store at boot. The rv64 asm RMW sites are non-atomic on a plain global (audit S3 #513) but cannot interleave: SIE==0 and the scheduler does not exist yet.
- INV-NEST-4: x86_64/aarch64 must observe NO STORE. Their bodies return the live value only, and the returned value is logged, so future drift is visible in the boot log instead of silently corrected.
- INV-NEST-5: the park predicates are frozen. arch::isr_context_park_denied() (irq_guard.hpp:92) and both callers keep exact semantics — no re-fork, no signature change.
- INV-NEST-6: the boot print must not use Logger formatting or allocation — debug_write/debug_write_hex only.
- Cross-arch parity: one declaration, three bodies, one call site; rv64 is the only behavior carrier and the other two are documented arch-equivalents (verify-only), which is the form the parity rule allows.
