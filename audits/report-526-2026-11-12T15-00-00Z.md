# SIL 3 Safety Audit — Issue #526: riscv64 split-L2 table teardown leak

- **Issue:** staycool1374-Ger/nexios#526 — [riscv64] VMM split-L2 table leaked on teardown, PMM+1 per split
- **Input:** `audits/pending_patch_526.diff` (fix commit vs parent)
- **Scope:** one functional line + comment in `src/kernel/memory/vmm.cpp` (`VMM::get_table` split branch); `test-history.txt` and `prompts/LEARNINGS.md` churn ignored (non-code)
- **Spec basis:** `prompts/CODING_STYLE.md`, `docs/specs/memory.md`
- **Verdict:** DECISION: APPROVED (no correction patch; findings below are all satisfied)

## 1. What the fix does

`VMM::get_table()` had two allocation sites with divergent ownership:

- create branch (fresh table): `user_alloc ? alloc_user_page() : alloc_page_table()` (vmm.cpp:320-321, unchanged)
- split branch (huge/block → 512-entry table): hardcoded `PMM::alloc_page_table()` (KERNEL-owned)

The fix makes the split branch match the create branch:

```cpp
uint64_t new_page =
    user_alloc ? PMM::alloc_user_page() : PMM::alloc_page_table();
```

A riscv64 user-map split (no inline split exists in riscv64's `map_page_in_pml4_try`, which relies on `get_table`; vmm_map.cpp:190-199) therefore now produces a USER-owned L2 that `free_user_pages()` actually frees (owner-bit gate, vmm_teardown.cpp:106-108), instead of a KERNEL-owned L2 it skips → PMM+1 leak per split. This converges riscv64 with the x86 inline-split precedent (`PMM::alloc_user_page()`, vmm_map.cpp:241).

## 2. Gate-by-gate audit

### (a) USER-owned split tables can never be shared across PML4s — PASS

Sharing would require one physical table page to be reachable from two live PML4s while USER-owned (teardown frees USER-owned tables per PML4 → double-free). Every clone/copy path was checked:

1. **`clone_kernel_pml4()` (vmm_clone.cpp:38-167):**
   - riscv64: user half `L0[1..255]` zeroed (51-53); `L0[0]` subtree **deep-copied** into fresh `alloc_user_page()` L1/L2 (76, 105) with USER entries stripped (95-98, 117-123) and MMIO/identity leaves copied **by value** (100-103, 1 GiB leaf 72-74). Each clone owns a private `L0[0]` subtree — no table page is shared.
   - Kernel half `L0[256..511]` copied **by value** (143-146), pointing at boot-owned tables. Those tables are KERNEL-owned (`alloc_page`, line 39), so `free_user_pages()` (which only visits indices 0-255 and only frees `is_user_page()`) never touches them. By-value kernel entries share *mappings by design* (spec §7.1.1 rule 2) but are never freed per-task — no double-free.
   - Non-riscv: user half zeroed (157-159), kernel half by value (162-164). Same conclusion.
2. **`deep_copy_user_pages()` (vmm_teardown.cpp:245-479):** never shares a table. Every level allocates a fresh `alloc_user_page()` destination (260, 295, 329 on x86/aa64; 405, 434 on riscv64) and memcpys leaf *contents*. Kernel-owned huge/block entries in the user index range inherit **by value** (290, 324, 400, 429 — issue #387 contract) as *entries*, and teardown skips them via the owner bit. No USER-owned table page ends up referenced twice.
3. **`merge_kernel_half()` (vmm_clone.cpp:248-262):** converges only `PML4_KERNEL_START..511` (level-0 start = `arch::PML4_KERNEL_START`). User-half split tables (indices 0-255, incl. riscv64 `L0[0]` which is below the merge start) are never merged/shared. riscv64 `L0[0]` is additionally excluded by construction.
4. **Split-inside-`L0[0]` sub-case (riscv64-specific):** a user task mapping a low VA (`L0 idx 0`) whose private L1 slot still holds a 2 MiB kernel MMIO/identity leaf will now split it into a USER-owned L2 whose 512 leaves are kernel frames copied by value. Teardown then frees the USER-owned L2 table while skipping each non-USER leaf (117-120) — exactly the pre-existing behaviour of the clone-installed `L0[0]` L1/L2 (also USER-owned, same walk). Private L1 per task ⇒ no cross-task aliasing; last-writer-wins hijack (the #221 defect class) cannot recur through this path.
5. **Double-free hardening (defence in depth):** even under a hypothetical double-reference, `PMM::free_page()` is idempotent — the `bitmap_test(index)` guard (pmm.cpp:717) makes the second free a no-op with no `ResourceTracker` delta (track only fires inside the set-bit branch, 718-720) — and `free_user_pages()` zeroes entries after freeing (`l1[l1_idx] = 0`, `l0[l0_idx] = 0`; vmm_teardown.cpp:124-128), preventing re-walk.

### (b) Pool-overlay / snapshot interplay — PASS

- `PMM::alloc_page_table()` is the **only** pool-range allocator (pmm.cpp:123, 676-706; sets `owner_set_kernel`, records `s_post_snap_overlay_`). `PMM::alloc_user_page()` (520-537) uses the general path and never touches the pool or the overlay.
- The fix therefore moves user-half splits **out of** the pool machinery — the same state x86 inline splits (vmm_map.cpp:241) have always lived in. Consequences, all benign:
  - `capture_pool_snapshot` / `restore_pool_snapshot` (pmm.cpp:1097-1143) only cover the pool range; user splits are covered by the full PMM bitmap+owner rewind (restore step 2, spec §6). No snapshot code asserts that split tables come from the pool; the manual-restore tests (`test_vmm_path.cpp:139-142`, `test_page_tables.cpp:285-290`) operate on **kernel-PML4** splits (see (c)/(d)), unaffected.
  - `PMM::free_page()` routes by range (pmm.cpp:727-741): pool pages return to the pool list (and clear their overlay bit, 736-738), general pages to the general list. Ownership-agnostic, idempotent — freeing a USER-owned general page and a KERNEL-owned pool page are both handled.
  - Overlay accounting improves (fewer post-snapshot pool insertions), never regresses.

### (c) Kernel-PML4 `map_page_try` callers unaffected — PASS

All kernel-table walks call `get_table` with the 3-argument form, so `user_alloc` defaults to `false` and the split branch still allocates `alloc_page_table()` exactly as before:

- riscv64: vmm_map.cpp:62 (`get_table(l0, idx[0], true)`), :83 (`get_table(l1, idx[1], true)`)
- x86/aa64: vmm_map.cpp:118, 123, 146 (pdpt/pd/pt descends)
- Walk-only uses (`unmap_page`, `virt_to_phys`, `pte_leaf_in_pml4`) pass `create=false` (vmm.cpp:447-554, vmm_map.cpp:301) — the split branch early-returns `nullptr` before any allocation regardless of `user_alloc`.

No kernel-half ownership, pool behaviour, or snapshot-rewind premise changes.

### (d) x86 / aarch64 behaviour change — PASS (convergent, no test-restore hazard)

On x86/aarch64 the `get_table` split branch with `user_alloc=true` now allocates USER-owned general pages instead of KERNEL-owned pool pages. This is a convergence, not a divergence: the x86 private-table inline split (vmm_map.cpp:236-252) already used `alloc_user_page()`. The `get_table`-level split on these arches fires only for defensive block-at-table-level cases (e.g. 1 GiB block where a table is expected); the common 2 MiB PD split is the inline site, already USER-owned.

Manual-restore hazard reviewed and clear:

- Every in-tree manual `free_page(split_pt)` (test_vmm_path.cpp:139-142, 176-179, 237-240, 352-359, 379-386; test_page_tables.cpp:285-290, 437-440) targets a **kernel-PML4** split produced via `map_page` / `map_phys_range_try(..., get_kernel_pml4(), ...)` with `user_alloc=false` — still pool pages, still freed correctly (`free_page` is range-agnostic in any case).
- No private-PML4 test manually frees a `get_table`-split table; private splits are reclaimed by `free_user_pages()`/teardown, which previously leaked them (the bug) and now frees them. No test can observe a new double-free: teardown zeroes entries post-free and `free_page` is idempotent (§2a.5).
- The aarch64 `kernel_half +1` note in the fix summary (kernel-PML4 tables never visited by `free_user_pages()` regardless of ownership) is accepted as correctly out of scope — consistent with spec §7.1.1 rule 4 and the x86-branch test-side manual-restore pattern.

### (e) IRQ / lock / flush hazards — PASS (none introduced)

- Locking: both allocators take `sync::IrqSpinLockGuard(pmm_lock_)` internally (pmm.cpp:521, 681); `get_table` itself holds no PMM lock, and the call contexts are unchanged. No lock-order or across-context-switch change (§11.1 unaffected — no spinlock is held across `reschedule` here).
- TLB/flush: the split fill (`vmm_arch_split_fill`) + link (`vmm_arch_table_link`) sequence and all `tlb_shootdown` sites are untouched; the only change is which free page backs the new table.
- Failure policy: the OOM path is identical (`return nullptr`, plus the preserved `#361` injected-fault gate at vmm.cpp:285-288 which now covers the split branch symmetrically with the create branch at 316-319). No new `ENSURE`, no behavioural divergence between debug/release (comment-only addition otherwise; CODING_STYLE §6-conformance holds). The privilege-escalation backstop (`ENSURE(PMM::is_user_page(phys))` for user-mapped managed RAM, vmm_map.cpp:206-209, 266-268) is orthogonal and still satisfied — table ownership does not weaken leaf ownership checks.

## 3. Style & contract compliance

- `docs/specs/memory.md` §2: "All newly allocated page-table pages MUST use `PMM::alloc_user_page()` for user-space hierarchies so `VMM::free_user_pages()` can free them" — the fix brings the riscv64 split site into compliance; previously it was the sole violator.
- Comment lines fit the 90-char comment allowance; `new_page` is initialised at declaration (§10.3); naming follows `snake_case` (§10.6); no `const_cast`, no new includes, no signature change (defaulted `user_alloc` preserved).
- Single-ownership discipline (§12.4): split tables remain single-owned by the enclosing PML4; teardown remains the sole releaser.

## 4. Residual notes (non-blocking, for testbed awareness)

1. Kernel-half splits (any arch) remain KERNEL-owned pool pages under an unwalked region (`free_user_pages` never visits indices ≥ 256) — reclaim stays test-side manual restore. Correctly left alone by this fix.
2. riscv64 `L0[0]` USER-owned tables holding kernel MMIO leaves (clone + new splits) are intentionally asymmetric (table USER, leaves KERNEL) and already handled by the leaf-skip + table-free walk. No action.
3. Gates cited by the developer (rv64 `memory_page_tables` 13/13 WARN-free, `cap_pager` roundtrip WARN-free, x86/aa64 zero-WARN, `proc_elf` + arch classes green, style Errors 0) are consistent with the static analysis but were not re-executed by this read-only audit.

## 5. Decision

**DECISION: APPROVED.** The one-line ownership parity is the minimal correct fix, converges all arches on the documented contract, introduces no sharing, snapshot, locking, or teardown hazard, and leaves every kernel-half path bit-identical. No correction patch required.
