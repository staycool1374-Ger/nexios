## FINDINGS

### [S3] src/kernel/daemon/daemon_mgr.cpp:240,337 — `regrant()` return ignored on restart/ensure paths
- **Rule:** error returns must be handled or explicitly justified (issue #348-A error-handling discipline).
- **Justification (non-blocking):** pre-existing pattern — both sites already ignored `grant_storage` failures identically before this slice; `regrant` itself is deliberately NOT `[[nodiscard]]`, so no new `-Werror` hazard is introduced. Failure mode is fail-safe: the daemon runs ungranted and the read path serves the already-pinned `RAMDISK_ERR_NOGRANT` degraded state. Boot-path caller (`kernel.cpp`) does warn-and-continue. Recommend a future slice either check-or-warn here for symmetry, but no correctness or leak consequence attaches: no REJECT.
- **Disposition:** note for follow-up, not a defect.

### [S3] src/kernel/test/test_ipc_throughput.cpp:78-82 — `recv` executes even if `sent` is false
- **Rule:** test asserts must not introduce hangs (fail-fast, no spurious block).
- **Justification (non-blocking):** `bool sent = send(...); bool ok = recv(out); JARVIS_ASSERT(ok && sent);` calls blocking `recv` unconditionally. Reachable-hang requires a refused self-`NONBLOCK` send on a drained inbox to a live task, which cannot occur (queue depth ≤ 1, `drain_self_inbox()` precedes, destination is `current_task`). The folded assert preserves single-branch benchmark overhead as claimed. No spurious-fire path exists in practice: no REJECT.

### [S3] src/kernel/ipc/ipc.cpp:332-341 — rollback `(void)transfer` failure leaves buffer with destination
- **Rule:** ownership transfer must be single-owner and leak-free on all paths.
- **Justification (non-blocking):** comment claim "stays with tcb and is reclaimed at task teardown (`BufferPool::unmap_all`)" verified against `task.cpp:2108` (teardown ordering: `unmap_all` before page-table teardown) and `transfer` being an atomic owner-swap (no double-ownership window, `buffer_pool.cpp:439-460`). If rollback fails, the buffer is owned by the live destination (reachable, usable, teardown-reclaimed) — never orphaned, never double-owned. The `(void)` rationale (teardown-recovery) is real, not convenience: no REJECT.
