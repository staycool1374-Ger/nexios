## FINDINGS

### [S3] `src/kernel/elf/elf_auth.cpp:133` — snapshot-site Span extent is `file_size`, not the buffer size
- Rule: a bounding view must be constructed with the extent of the object it
  views; doc claims must match implementation.
- `snapshot_ro_baseline` receives `const uint8_t *phdr_image` (raw, extent
  unknown) and fabricates `Span(phdr_image, file_size)`. Its sole production
  caller (`elf_loader.cpp:1769`) passes the packed staging buffer `phdr_image_`
  whose true extent is `sizeof(phdr_image_)` = 3648 (`elf_loader.hpp:236`), not
  the whole-file `file_size`. The `elf.hpp:221` claim "Whole file image view
  (bounds all reads)" is therefore false at this site: strides in
  `(3648, file_size]` would pass the bound check yet read past the static array.
- Justification for S3 (not S2): unreachable today. The load path enforces
  `phnum*phentsize <= 3584` (`elf_loader.cpp:1414-1419`, unchanged) and
  `validate_header` caps `phnum <= 64`, `phentsize >= 56` (`elf.hpp:138-143`),
  so max stride is `64 + 3584 - 56 = 3592 < 3648` — always in-bounds regardless
  of the inflated extent. Only in-patch `collect_ro_ranges` caller search
  confirms no other production/test caller. The patch strictly improves on
  baseline (which had zero bounds checks). Latent trap only: a future caller
  with unvalidated `phnum`/`phentsize` over a packed buffer would inherit a
  false bound.
- Follow-up (next slice, not blocking): thread the true extent — e.g.
  `snapshot_ro_baseline` takes `Span<const uint8_t>` (caller passes
  `sizeof(phdr_image_)`) — and correct the `elf.hpp:221` doc to name the packed
  buffer, keeping `file_size` solely for `validate_segment`.

### [S3] `src/kernel/elf/elf_auth.cpp:53-59` — stride overflow check catches additive wrap only
- Rule: overflow guards must cover every wrapping operation.
- `stride = i*phentsize + phdr_buf_off`; `if (stride < phdr_buf_off) continue`
  detects wrap of the addition but not of the multiplication `i*phentsize`
  (`i` is `uint16_t`, `phentsize` unconstrained above by `collect` itself).
- Justification for S3: memory safety does not depend on this check — the
  immediately following image-bounds test (`stride > size || sizeof > size -
  stride`, off-by-one verified correct incl. the `stride == size` edge, and the
  subtraction is underflow-safe due to `||` short-circuit) rejects any
  out-of-image stride however produced; worst case is an in-bounds alias,
  further gated by `PT_LOAD` + `validate_segment(file_size)`. Hardening
  suggestion: divide-back/multiply-checked stride or an explicit
  `phentsize >= sizeof(PHDR)` precondition assert at function entry.
