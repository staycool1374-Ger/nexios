## INVARIANTS & CONCURRENCY BOUNDARIES
- IOPB ledger mutation (add/clear/drop) is serialized by the existing `g_iopb_lock` (same lock as `g_iopb_claimed`/pool). **Lock order invariant (unchanged):** `scheduler_lock_ -> g_iopb_lock`, never reverse. `iopb_ledger_clear_cap` runs from MmioCap::dispose/revoke — task context only, never under a cap/CNode spinlock (dispose may run on the 1→0 ref transition; ledger holds no cap reference, only a pointer used for matching, so no deadlock; the pointer is not dereferenced, only equality-compared — never UAF).
- MmioUserMap registry mutation is task-context only; guard with a single static SpinLock (never held across `VMM::map_*`/`unmap_*` PMM/mempool paths — claim/find under the lock, map outside). Registry slots are keyed by `owner_task_id` + a `gen` (recycled-slot stale-handle defense, IrqDelivery pattern). A dying task's `drain_task` runs in `cleanup()` (task context).
- **No dynamic allocation on RT paths:** both the map registry and the IOPB ledger are static bounded arrays (`CONFIG_CAP_MAX_MMIO_MAPS`, `CONFIG_IOPB_MAX_GRANTS`); exhaustion fails closed (returns -1 / refuses).
- Revocation is fail-closed but not retroactively destructive of device memory (never PMM-owned): clearing IOPB bits re-denies port access; unmap removes the user PTE; a revoked cap refuses any future map/grant (already the `map_mmio_from_cap`/`lookup` behavior).
- **TCB sentinel gotcha avoided:** neither design adds a new TCB scalar field — the map registry is keyed by task id in a static table and the ledger is in the IOPB layer. If any implementation deviates and adds a TCB field, it MUST be initialized at all 4 memset sites (create/create_user/clone at task.cpp:897/1131/1313 and elf.cpp:491) — the plan forbids this deviation (prefer the static registry).
- ResourceTracker: maps and ledger entries must not create untracked resources; the MmioCap count already folds into `cap_objects`; device pages are never PMM-tracked. snapshot_restore resets the map registry and the IOPB ledger (add to `iopb_snapshot_reset` + a new `MmioUserMap::snapshot_reset`).

## SIL 3 / SAFETY RISKS
- [S1] Retroactive IOPB revocation correctness — clearing bits re-denies live port access; must use the same bit math as grant_range and re-load the TSS when the affected task is the loaded owner, else a denied port stays allowed (privilege leak). Mitigation: ledger_clear_cap re-sets bits 1 and `GDT::iopb_load` on owner match; tested by `ioport_revoke_clears_live_bits`.
- [S1] Stale VA reuse in the map registry — a recycled slot/VA must not alias another task's device mapping (cross-task device access). Mitigation: registry keyed by `owner_task_id` + `gen`, drain_task on cleanup, gen bump on slot release; unmap by VA re-validates owner.
- [S2] Ledger/map-pointer UAF — the ledger stores a raw `cap_ptr` for matching only; dispose may free the cap. Mitigation: the pointer is never dereferenced, only equality-compared; `ledger_clear_cap` runs during dispose/revoke before `MemPool::free`; document the non-owning contract.
- [S2] Lock ordering / spinlock scope — ledger and registry guards must never be held across `VMM::map/unmap` (PMM/mempool locks) or `reschedule`. Mitigation: claim under lock, map outside; document `scheduler_lock_ -> g_iopb_lock -> mmio_map_lock` order.
- [S2] User VA window collision with heap/stack/ELF segments — a fixed window that overlaps `mem::HEAP_VADDR`/`STACK_VADDR` corrupts user memory. Mitigation: `static_assert(BASE + MAPS*REGION <= STACK_VADDR)` and no overlap with HEAP; validate at build.
- [S3] Ledger-bound overflow silently weakening revocation — a full ledger degrades revoke-rollback. Mitigation: reserve the ledger entry BEFORE the grant; ledger-full fails the grant closed (no partial grant without a ledger record).
- [S3] Debug/release divergence — revocation/registry behavior must be identical; CONFIG_DEBUG may only add asserts/logging.

## OPEN QUESTIONS
- Should `SYS_MMIO_UNMAP` take a raw VA (requires the task to remember the returned VA) or the cap handle? Recommend VA (simpler, mirrors a real driver holding the returned base); confirm no existing user ABI expects a handle-based unmap.
- Does revoking a memory MmioCap need to **immediately** unmap an already-mapped device PTE, or is refusing new maps + unmap-on-cleanup acceptable? Recommend immediate unmap of the owning task's PTE for fail-closed SIL 3 parity with the IOPB closure; confirm the auditor accepts the immediate-unmap cost on the dispose path.
- Exact `CONFIG_USER_MMIO_VA_BASE` value — must sit below `mem::STACK_VADDR` (0x70000000) and clear of the heap (0x60000000) and the ELF segment upper bound (`< HEAP_VADDR`); pick the concrete base/region at implementation time and verify against the boot layout.
