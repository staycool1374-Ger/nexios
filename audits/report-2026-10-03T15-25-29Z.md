## FINDINGS
- [S1] §9.2(b) pre-add entry-breakpoint insert ("sel3 semantics ... BEFORE
  `add_task_err`" + "zero instructions execute unobserved") — UNSOUND
  ORDERING + SILENT FAILURE PATH
  WHY: the sel3 insert path requires a live bound target —
  syscall_handlers_debug.cpp sel3→`debug_resolve` (live `find_task` +
  generation match + `debugger_id == caller`) and
  debug_stop.cpp `debug_bp_insert` returns false when
  `target.debugger_id == 0`. Pre-add there is no live task and no
  claim/grant yet (`debugger_id == 0`), so the insert as specified cannot
  succeed; §9.7 defines no return-check/teardown for pre-add bp failure
  (it covers only loader / spawn / post-add claim-grant-stop), so the flow
  proceeds to add/run on the sel9 belt alone, which parks only at the next
  user-mode boundary per §4 — first instructions can execute unobserved
  with no teardown trigger. The load-bearing safety guarantee is unprovable
  as written. It also contradicts §9.4's own premise (`find_task` requires
  a live target — the same liveness the bp insert needs).
- [S2] §9.2(e) / §9.7 teardown ("`terminate_and_drain`" + "entry breakpoint
  clears via the shared disposition path") — UNDEFINED MECHANISM + LEAK
  WHY: `terminate_and_drain` exists only in kernel/test helpers, not as a
  production scheduler API; production distinguishes never-added
  `destroy_completed_tcb` from admitted-task teardown, so the spec names a
  helper the implementation cannot call. The shared disposition (§14.5 /
  `debug_apply_disposition`) restores bp shadows only for bound targets;
  for claim/grant-failed (never bound) or add-denied (never live) targets
  there is no binding slot, and §14.5 text never defines bp-shadow clearing
  for unbound targets — a pre-add table entry keyed by (id/gen) has no
  defined clearer and leaks a bounded kBpCap slot.
- [S2] §9.5 on-demand spawn ("existing boot daemon-spawn helper",
  "debugd pid cell", "init/shell task context") — UNDEFINED TERMS +
  SUPERVISION GAP
  WHY: no runtime spawn-one-daemon helper is named — taskdefs offers
  `reboot_from_table` (noreturn, kills all tasks) plus read-only accessors,
  not a shell-callable spawn entry, so a boot-path helper invoked at runtime
  has unproven preconditions (locks, IRQ, admission). The pid cell
  (taskdefs.cpp `g_debugd_pid_cell` + accessors) has no spec owner/lifecycle
  (who sets on spawn/death, stale-generation handling). "init/shell task
  context" is ambiguous, and excluding DaemonWatch (kernel.cpp, vfsd/iocd/
  watchdogd only) leaves #191 supervision/restart of an on-demand debugd
  undefined (§10 debugger-death disposition still holds, restart
  responsibility does not).
- [S2] Bare sel3/sel7/sel8/sel9 numbers in §9.2–§9.4 and §12 item 5 —
  UNDEFINED + SCOPE CREEP (checks 4 + 5)
  WHY: normative spec defines only attach(0)/attach(1) (§3) and defers the
  grant-selector number to implementation (§14.2 "number assigned at
  implementation"); control selectors are named by function in §13.4, never
  numbered. §9/§12 concretize 3/7/8/9 without updating §3/§14.2, so a
  spec-alone reader cannot resolve them and the acceptance sequence
  (claim(sel1)→grant(sel7)→stop(sel9)) tests undefined numbers.
- [S2] §9.6 "exposes NOTHING beyond §4 snapshots + `read_regs`/`read_mem`" —
  OVERBROAD ABSOLUTE, self-contradiction (checks 1 + 6)
  WHY: read literally it forbids `write_regs`/`write_mem`/`break_at`/
  step/continue/stop that the §9 session itself requires (§9.2 entry bp is
  a target-memory write; §9.4 sel9 stop; GDB continue/step). The second
  clause (no new syscall, no scheduler-state write path) is sound and
  consistent with §9 sentence 2, but the first clause bans the §4/§6
  debug-control plane the delta depends on. "NOTHING" is also an
  untestable absolute.
- [S2] §12 item 5 acceptance — INCOMPLETE / UNTESTABLE (check 6)
  WHY: "entry-bp present before add_task" has no observable predicate
  (target not live, no probe defined); "`runelf --debug a b` usage
  contract" tests behavior §9.1 never defines (multi-arg disposition and
  message); teardown covers only grant-refusal and spawn-failure while
  §9.7 normatives claim/grant/stop failures each (claim/stop teardown
  uncovered); the denial enumeration omits the resolve-path `EBADF`
  (§14.4) without scoping to the mint path.
- [S3] §15 Q5 "implementer may pick refuse-EBUSY as default" — unspecified
  observable
  WHY: Q-section discretion without an errno/surface/state predicate; two
  conforming builds (queue vs refuse vs second-target) diverge with no test
  to distinguish. State the refusal contract or mark explicitly deferred.
- [S3] §9.1 / §9.7 usage/error predicates vague
  WHY: "the normal `runelf` usage line" and "shell error naming the errno"
  name no exact string/surface; argv edge cases (flag position, lone
  `--debug`, extra args) are left to implementation without a contract.
