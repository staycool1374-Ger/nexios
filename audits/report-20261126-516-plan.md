## FINDINGS
- [S1] audits/plan-516.md Step 4 (L74-79) — publish placed before the AP-live retention check announces a still-executing AP corpse
  WHY: Watchdog/deadline victims are marked TERMINATED while possibly current on another CPU; publish() calls daemon::notify_death (clears the daemon PID cell, scheduler_terminate.cpp:63) and latches the DeathNotify record, so a supervisor/restart poller starts a second instance while the old corpse still runs. INV-K9's `state == TERMINATED` guard does not exclude AP-live TERMINATED (is_current_on_any_cpu, scheduler_lifecycle.cpp:1163). Correct order is AP-live check first (retain + carry cause, no publish), publish only for non-AP-live TERMINATED && !teardown_completed_, with the retained entry publishing on a later pass once descheduled. This also answers OPEN QUESTION Q2: publish-at-decision is correct only for non-AP-live corpses.
- [S2] audits/plan-516.md INV-K1 + Step 9 (L20, L99-100) — single-choke scope over-broad and grep gate unsound for daemon::notify_death
  WHY: kernel::daemon::notify_death is the daemon manager's own registry clear (defined daemon_mgr.cpp:123, called unqualified at daemon_mgr.cpp:192 and :480), not the death-record publish. INV-K1 forbids all direct daemon::notify_death callers except the teardown backstop, which misclassifies the owner's legitimate self-clears; worse, the Step-9 grep for the qualified string misses the two unqualified production callers, so the gate passes while direct callers exist (false-negative enforcement). Fix: scope the choke to DeathNotify::on_task_death only; rewrite the gate to match qualified and unqualified notify_death across src/kernel/{daemon,task}/ with an enumerated allowlist (publish_task_death + complete_teardown backstop task.cpp:3082-3090 + daemon_mgr self-clears :192/:480).
- [S2] audits/plan-516.md INV-K3 (L22) — birth-site enumeration undercounts (four vs five + init-list)
