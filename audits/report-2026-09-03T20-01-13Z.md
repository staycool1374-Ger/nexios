### New finding
- [S1] **Multi-page FrameCap teardown is partial: SYS_FRAME_UNMAP / revoke / drain clear only the base PTE, leaving pages 1..N-1 user-mapped into frames that a later cap dispose frees.**
  - `FrameUserMap::unmap` (frame_map.cpp:174), `invalidate_cap` (frame_map.cpp:215) and `drain_task` (frame_map.cpp:239) each call `VMM::unmap_frame_from_cap(va, pml4)`, which clears **one** PTE (`map_page_in_pml4(virt_addr, 0, false, pml4)` — vmm.cpp:1320-1322), while `VMM::map_frame_from_cap` maps **all** `fc->count` pages (vmm.cpp:1312-1315). The MMIO analog loops over every page (`unmap_mmio_from_cap`, vmm.cpp:1344-1350); the frame path does not.
  - Reachability: `SYS_FRAME_CREATE` accepts `count` up to `CONFIG_CAP_MAX_FRAME_MAPS` (8) and `count>1` maps fine (region is 2 MiB); the roundtrip test itself uses a 2-page cap, the producer/consumer test a 4-page cap.
  - Impact: after `SYS_FRAME_UNMAP` (or `FrameCap::revoke`), pages 1..N-1 remain present+user-writable in the task's PML4. When the owning CNode slot is removed/revoked and the last reference drops, `FrameCap::dispose` frees the frames (frame.cpp:55-56) and recycles them; the live task's stale PTEs then alias arbitrary recycled physical memory — user-reachable dangling PTE (memory-safety / privilege-boundary violation) and a direct violation of INV-SHM3/4 ("no PTE outlives the cap's frames").
  - Why the suite did not catch it: `frame_user_map_unmap_roundtrip` (count=2) asserted only `live_count()==0` (registry empty) and self-terminated the task immediately, freeing the cloned PML4 wholesale — it never inspected the second page's PTE.
  - Fix (included in audits/rejected_patch.diff): capture `fc->count` under `s_lock_` (pin held) at the slot-find step and loop the unmap over all pages in all three call sites; strengthen `frame_user_map_unmap_roundtrip` to park the task after `SYS_FRAME_UNMAP` and assert `virt_to_phys_in_pml4` is 0 for **both** the base and the second page before terminating.
