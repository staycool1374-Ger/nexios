## INVARIANTS & CONCURRENCY BOUNDARIES
- INV-1 **Latch is allocation-free and lock-free from every context.** The latch body is limited to: atomics, `arch::Timer::ticks()`, and `log::dmesg_push_sev` (fixed ring, no lock, no allocation). No `Logger::*`, no format string, no `MemPool`/`PMM`, no blocking call may ever enter this path. It must stay callable from inside `pmm_lock_` (`alloc_page` budget deny), from inside `mempool_lock_` (`MemPool::alloc`), and from any IRQ state.
- INV-2 **Lock order.** Canonical ranks are `Sched(1) → Queue(2) → Leaf(3)` (`docs/specs/irq-preemption-contract.md` §2); `pmm_lock_` / `mempool_lock_` / `pool_lock_` are unranked and must never be *outer* to `scheduler_lock_`. Therefore the latch **never** pokes a supervisor (a poke reaches `set_task_ready`, i.e. `scheduler_lock_`), and the only poke site is `on_tick`'s lock-free tail, where the adopted scheduler scope has already closed (lines 1114–1117). `Notify::lock_` is Unranked and the poke holds no other lock.
- INV-3 **Single latch, monotone count, one authoritative record.** First caller wins the latched state (`reason`, `latch_tick`); every caller bumps `count()`; exactly one warning row is emitted by the winner; a caller may emit its own subsystem row only when `latch_notable()` says the ordinal is a multiple of 64 (Liu–Leyland style), so sustained exhaustion cannot flood the fixed ring.
- INV-4 **Production clear never happens.** `clear()`/`snapshot_reset()` are test-isolation seams only; the only production recovery from a latched warning is reboot (Q12-A / non-goal "no recovery"). No syscall path clears the latch.
- INV-5 **Fail-closed, never silent.** If no supervisor is registered, `pending_notify()` stays set (the record survives and is delivered to the first supervisor that registers). `service_pending()` must only clear pending after a supervisor has been resolved and poked; a stale slot never dereferences a freed TCB (id + generation re-validated through `Scheduler::find_task`, mirroring `DeathNotify::on_task_death`).
- INV-6 **Watermark baseline is post-freeze, not total RAM.** After M4 handover, handed-over pages leave PMM accounting, so `free/total` at boot can already be far below 90% → comparing against `total_memory()` would latch spuriously on every bootstrap boot. Baseline = `PMM::free_memory()` sampled on the first tick after `PMM::is_frozen()`; trip when `free_now * 100 <= baseline * (100 - threshold_pct())`, evaluated only when `baseline > 0` (no division, no overflow for any sane RAM size).
- INV-7 **Zero-alloc emit from every OOM leg.** Every emission site added here is inside a region where allocation is impossible by construction (the caller is returning a deny), so the warn path must not introduce the first allocation-capable call in that window.
- INV-8 **Cross-arch parity.** No arch-conditional code; the same TU set, the same syscall numbers, the same record layout on `x86_64`, `aarch64`, `riscv64`.

### Increment 1 — warn-path completeness (committable and auditable on its own; no ABI change)
1. `mem_pressure.hpp`: add `MEMPOOL_EMPTY = 6` and `PMM_PRESSURE = 7` to `MemPressureReason`; declare `uint64_t latch_tick() noexcept`, `bool latch_notable(MemPressureReason) noexcept`, `bool take_pending() noexcept`, `void snapshot_reset() noexcept`; delete `drain_pending()`; rewrite the file comment to state single-shot-per-boot semantics, that the static state is the authoritative record and the dmesg row is a best-effort diagnostic copy, and that `clear()` is test-isolation only.
2. `mem_pressure.cpp`: introduce a file-static `uint64_t latch_ordinal(MemPressureReason) noexcept` that performs the relaxed fetch-add on `count`, the first-wins CAS on `latched`, and (winner only) the `reason` / `pending` / `latch_tick` stores plus the `PMM+4` row; implement `latch()` as a thin wrapper; implement `latch_notable()` as `(latch_ordinal(r) % 64) == 0`; implement `take_pending()` as an atomic exchange to `false`; implement `snapshot_reset()` zeroing latched/reason/pending/latch_tick/observed_tick/count; include `<kernel/arch/timer.hpp>`.

## SIL 3 / SAFETY RISKS
- [S1] Watermark compared against total RAM would latch on every `CONFIG_MEM_MGR_BOOTSTRAP=1` boot (handover removes pages from PMM accounting) and could trip the fail-safe machinery spuriously — mitigation: INV-6 post-freeze baseline, plus a QE test proving no latch with an unchanged baseline.
- [S1] Calling the supervisor poke from any path that holds `pmm_lock_`/`mempool_lock_`/`pool_lock_` or the scheduler lock would invert the canonical order (`Sched` outermost) and can deadlock against `set_task_ready` — mitigation: single poke site in the `on_tick` lock-free tail (INV-2), with the site comment and a `core_sync` run under `CONFIG_IRQ_CONTRACT_ASSERT`; any second poke caller is a REJECT.
- [S1] Any allocation-capable call (`Logger`, formatting, `MemPool`, `PMM`) added to the latch path would be reachable from inside `pmm_lock_`/`mempool_lock_` and from OOM legs — mitigation: INV-1 body allowlist, and the reviewer checks that the only calls are `Timer::ticks` + `dmesg_push_sev`.
- [S2] `dmesg` is a single-producer/single-consumer fixed ring; the warn path can be entered from two CPUs, so a row can be overwritten or echoed — mitigation: the authoritative record is the static latch state and `RECV` never reads the ring; rows are budgeted 1-per-64 (INV-3). Accepted residual, documented in `oom-rt.md` §6.
- [S2] The warning row can be evicted from the ring by later traffic before a supervisor reads it — mitigation: same as above; `RECV` returns `reason`/`count`/`latch_tick` from latch state.
- [S2] Supervisor-slot squatting: any task could claim the slot and swallow the warning — mitigation: refuse while a different live occupant holds it, takeover only when the occupant is dead (fail-closed), trust model = boot order, and a capability gate is a named follow-up.
- [S2] New syscall numbers are positional in `syscall_table_`; an enum/table mismatch silently misroutes a syscall — mitigation: the `static_assert` pins on entries 105/106, plus `core_syscall`/`syscall*` classes in the gate list and a check that `SYS_MAX == MAX_SYSCALL`.
- [S2] Existing QE tests assert exact latch counts and already flake (evidence above); landing new trip sites makes exact-count assertions strictly more fragile — mitigation: the QE retarget item is a prerequisite for the green gate, not a follow-up.
- [S3] `pending_notify()` can stay set indefinitely when nobody registers — harmless by design (INV-5), but must be stated in the spec so it is not "fixed" later.
- [S3] `MemPressureReason` growth changes the dmesg `context` values; the trip-site table in `oom-rt.md` §6 is the single mapping and must land with the enum.
- [S3] retype `SHORT_RANGE` / `CAP_ERR_OBJECT_EXHAUSTED` are deliberately unlatched (client-policy error; MemPool exhaustion is caught at its own site) — documented so a future reader does not add a spurious latch.
