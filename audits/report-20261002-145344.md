## FINDINGS

### [S1] `src/kernel/task/scheduler.cpp:5479` — generation-mismatch skip fail-open: armed watchdogs never fire
**WHY:** `scan_watchdogs_locked` skips expiry when
`t->wdog_gen != t->generation && t->wdog_gen < t->generation`.
But the two counters live in different domains: `t->generation` is the global
creation sequence (`task.cpp:301-305`, `s_next_generation` from 1, fresh value per
TCB at `init_task_common` — never a slot-reuse counter), while `t->wdog_gen` is a
per-TCB arm counter starting at 1 (`syscall_handlers_watchdog.cpp`, `++t->wdog_gen`).
For any task created after the first `generation`-many tasks (i.e. virtually every
task: e.g. 10th task has `generation=10`, first arm gives `wdog_gen=1` → `1 != 10
&& 1 < 10` → skip), an armed watchdog is skipped forever. No TIMING+6 ring record,
no KILL — the fail-closed default (CONFIG_WATCHDOG_ACTION=3) is silently defeated.
Firing depends on arm-count vs boot-task-count (nondeterministic). TCBs are freshly
MemPool-allocated per creation (no slot reuse), and staleness is already covered by
disarm-on-teardown (`task.cpp` `cleanup()`), never-armed `wdog_gen==0`, and the
`TaskFields` capture/restore rewind — so the check guards a nonexistent ABA vector
while killing the safety function. Fix in `audits/rejected_patch.diff`: delete the
3-line check; keep the `!armed || wdog_gen==0` skip.

### [S3] `src/kernel/vfs/procfs.cpp:1682` — `self_lookup` uses a shared static `PidWatchdogVnode`
**WHY:** `static PidWatchdogVnode cur_wdog` is mutated on every `/proc/self/watchdog`
lookup (pid/task/parent rewritten). Concurrent lookups from two tasks tear the
shared object (stale `task` pointer → wrong-task field read). Non-blocking: read-only
consumer, mirrors the adjacent `cur_stat` precedent, no corruption of kernel state.
Recommend matching whatever disposition the `cur_stat` precedent carries, or a
per-call stack vnode. No REJECT.
