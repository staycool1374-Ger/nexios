## FINDINGS

- [S1] `audits/plan-555.md` steps 5+8e — eager child-slot removal prunes grandchild edges before the walk takes them; transitive revoke silently degrades to depth-1
  WHY: Step 5 hooks `derivation::forget_slot(*this, idx)` into `CNode::remove(idx)`, dropping edges where the slot is parent **or** child. Step 8e then orders `child_node->remove(child_slot)` **before** pushing the child work item ("which prunes grandchildren edges via step 5" — the plan names the pruning but misses the consequence). Grandchild edges have `parent == (child_node, child_slot)`, so they are already gone when the walk later calls `take_child` on the pushed item. A chain A→B→C revoked at A destroys B and silently leaves C live. This defeats the issue's core mechanism — spec §4.3 "destroys all derivations of the named cap" (`microkernel-transition.md:250-251`), INV-MK-7 (`:80`), and §10 D4 supervisor-restart revoke (`:725`) — with a success return (silent wrong-success on a safety function). The plan's own `cap_revoke_derivations_depth_bound` test (chain of 8, "revoking the root clears exactly the existing chain") would fail under this design; the test is sound, the step is wrong. Fix: per-item drain-then-remove (loop `take_child` to exhaustion, resolving+pushing each child, and only then `remove` the item's own slot), with an explicit root exemption (the named slot must survive per §4.3). The 9-entry DFS stack and the `kCapMaxDerivations` trip counter still bound the fixed walk.
- [S2] `audits/plan-555.md` Q2 (`:81`) — §4.3 revoke-time typed-error + resumable-over-bound behavior replaced by creation-time enforcement without owner sign-off
  WHY: §4.3 is normative SHALL: "a revoke that exceeds the bound returns a typed error and is resumable" (`microkernel-transition.md:252-253`). The plan enforces `child_depth <= CONFIG_CAP_MAX_DEPTH` at derivation creation and makes the revoke-side bound unreachable, with no resumable path. Creation-time bounding satisfies "revocation depth is bounded" but does not implement the mandated revoke-time contract. The plan is transparent (Q2 records the deviation and the re-plan trigger), but transparency is not closure: a normative SHALL deviation requires the owner decision recorded on the issue **before** implementation begins. Gate the build on the Q2 sign-off.
- [S2] `audits/plan-555.md` step 8a (`:42`) — named-slot validation locking unspecified; lock-free slot-state read races `CNode::remove` gen bump → wrong-success on recycled slots
  WHY: Step 8a lists "slot occupied, `handle_gen == slot.gen`" with no lock, while the existing `cap::revoke` performs the identical occupy-claim validation **under** `cspace->lock_` (`src/kernel/cap/cap.cpp:210-215`) and `do_copy_pinned` re-checks gen after the lock (`cap.cpp:268-287`). A slot recycled between a lock-free 8a read and the walk yields no `take_child` match (gen mismatch) and step 8g returns `CAP_ERR_OK`/`0` — success reported for a handle the caller does not own. That is a deny-never-degrade (INV-MK-9, `:81`) violation. Fix: validate 8a under `cspace->lock_` with the `do_copy_pinned` gen re-check pattern.
- [S2] `audits/plan-555.md` step 9 (`:43`) — "verbatim" rollback reuse is inaccurate and incomplete; record-failure leaves the installed child Untyped live
  WHY: The cited block (`src/kernel/cap/untyped.cpp:300-309`) runs when child **install** failed (`idx_child < 0`), so no slot holds `child`. On the plan's record-failure path both installs **succeeded**: `idx_child` (declared `untyped.cpp:298`, scoped inside `if (child)`) is out of scope at the insertion point, so the reuse cannot be verbatim, and the verbatim body (`remove(idx_target)` + releases, no `remove(idx_child)`) drops the creator ref while the child slot stays occupied — a failed retype with `CAP_ERR_DERIVATION_FULL` leaves a live child Untyped installed (partial side effect; breaks the no-partial-grant precedent the same file enforces). Memory safety holds (prefix freed once via target dispose, remainder owned once by the live child — verified against `untyped.cpp:261-279`), but the contract does not. Fix: hoist `idx_child` to outer scope and on record failure `remove` **both** slots before releasing.
- [S3] `audits/plan-555.md` INV-DERIV-1 (`:24`) — new `derivation_lock_` (and incumbent `CNode::lock_`, `src/kernel/cap/cap.hpp:65`) are both rank-`Unranked`, so the M2 §6.2 order check is blind to future nesting
  WHY: `spinlock_order` flags only ranked inversions (`src/kernel/sync/spinlock_order.cpp:151-159`); no `set_rank` exists anywhere under `src/kernel/cap/`. The never-together discipline holds for this design by construction (scoped `SpinLockGuard`s, sequential primitive calls — verified at all three call sites: record-after-install-return, forget-after-guard-exit, take/lookup sequencing), so this is hardening, not a defect. Recommend assigning `LockRank::Leaf` to `derivation_lock_` so any future nesting reports instead of silently inverting.
- [S3] `audits/plan-555.md` appendix (`:101`) — two anchor inaccuracies (freshness, not substance)
  WHY: (a) "`parent_`/`depth_` declared-and-never-written" (`cap/cap.hpp:59-141`): `parent_` is indeed write-free (sole mention `cap.hpp:63`), but `depth_` **is** written — `child->depth_ = node->depth_ + 1` (`src/kernel/cap/cap.cpp:87`, read at `:84`). No design impact (the derivation table does not consume either field; the `CNode::revoke` cascade path is untouched). (b) Arch citations omit the directory: actual paths are `src/kernel/arch/aarch64/test_aarch64.cpp:1223` and `src/kernel/arch/riscv64/test_riscv64.cpp:689` — line numbers and the `MAX_SYSCALL`-symbol (not literal) claim both verify. Correct the paths when the plan is revised.
- [S3] Spec traceability follow-ups the plan correctly defers (owner-gated, §582 precedent) + one capacity note
  WHY: (a) Adding syscall 98 makes §3.4's derived counts (`:214-215`, "47+5+46 = 98 = MAX_SYSCALL") stale and leaves T-1 without its N6 row; INV-MK-7's VIOLATED status (`:80`) needs its flip. File the owner-gated spec follow-up at implementation time (do not edit the spec in the dev lane). (b) `kCapMaxDerivations = 256` is a new unmeasured number (no Q7 cover — verified Q7 list at `:890` has no derivation bound); the "≥ 4× a full 64-slot fill" rationale plus the F9/`#562` re-home note (Q3) make it acceptable, and table-full fails closed with a typed error. Note the availability edge: a busy granter can fill the table and newly fail previously-working grants; consider a debug-visible fill counter at implementation time.
