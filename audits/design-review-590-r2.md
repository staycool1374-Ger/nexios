## VERIFIED RESOLVED (r1 findings, per-fix verification)

### [S1-a] INV-WAIT-6 consumption precedence — RESOLVED, sound
- Writer-set claim verified by grep: writers of a parent's `waiting_child_pid` in production are exactly (i) the waiter's own publish (`syscall_handlers_process.cpp:148`) and (ii) the wake's clear (`scheduler_lifecycle.cpp:502`, `syscall_handlers_misc.cpp:166`, `syscall_handlers_thread.cpp:218`). `task.cpp:1810,2212` zero the field of a NEWLY CREATED TCB (different object, never the observed location). `services/shell.cpp:2209` is read-only diagnostic. Test TUs write only harness TCBs. Snapshot restore (`scheduler_snapshot_fields.cpp:57`) rewrites the field but is harness-only (see O1).
- After-fence `!= target_pid` is therefore a sound consumed-proof: the only post-publish transition away from the just-stored value is the wake's clear. Compare-vs-target (not vs 0) plus the pathological-target-0 argument holds: no task carries id 0 (ids allocate from 1 up, `scheduler_id_table.cpp:72-94`), so target 0 never publishes (scan misses, early -1) — the sentinel can never alias a real publication.
- `waiting_child_status` correctly rejected as indicator: `deliver_wait_status` clears it on BOTH legs (`scheduler_lifecycle.cpp:437-441`), so it cannot distinguish delivered from consumed-but-unfaulted. Correct.
- Outcome mapping (never undo / never -1 / never block on consumed; resolve via top-of-loop collect) is the only safe shape: undoing a delivered wake strands a parented zombie (the r1 kill-chain), and the wake already readied the parent + patched its trap frame, so re-resolution converges on the same child id.

### [S1-b] Second residence + retention — RESOLVED, sound
- `zombie_lock_` exists (`scheduler.hpp:1624`) and is the right lock: canonical order `scheduler_lock_ > zombie_lock_` (`scheduler.hpp:1454-1462`); all four drains already take IrqGuard+leaf with no global held. The new collect takes the same leaf-only shape — no new order edge. IrqGuard nests (depth counter, `irq_guard.hpp:105-178`), so calling `try_claim_teardown` (which takes its own IrqGuard, `task.cpp:3107-3120`) under the leaf is safe.
- Pop+claim atomicity holds: unlink and claim both occur under the leaf, serializing against all four drain pops cross-CPU. The deferred-kill destroy path cannot race a released corpse: `kill_declined` declines it at BOTH arm (`defer_kill`, `:835`) and process time (`:879`, `find_task != task`) — "dropped, not retained: the owner completes the tail". On claim failure the plan re-links at the tail and reports not-collected (never double-free, never leak: the winner owns the full tail per the #409 contract).
- Owner-death escape is sound and leak-free: predicate false when the owner is gone/TERMINATED, so the corpse frees normally. The watchdog-skipped shape (never released, stays parented/in-table) is covered by `reap_orphans`: parent-TERMINATED or parent-absent ⇒ `can_reap` (`scheduler_lifecycle.cpp:653-672`); live parent ⇒ deferred (Unix zombie semantics, `#221`). No new leak path.
- #523 traced: fault-kill without waiter → wake finds no match → flag never set → drain frees immediately, exactly as today. The flag is set ONLY at the wake match point, so #523's release restoration (trap kills now zombie-list via `terminate_err_from_trap`, `scheduler_terminate.cpp:240-287`) is untouched.
- Waiter-side single-writer claim holds: the flag is written only by the terminator in its own critical section, never by the waiter — no new SB pair. (Wording nit filed as O2.)
