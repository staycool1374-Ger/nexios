## 1. What the fix does (3 src hunks, riscv64-only)

1. `smp.hpp` — declares `kernel::smp::note_shootdown_applied()` + widens
   `shootdown_applied()` doc from "entries applied by AP ISR runs" to
   "remote-fence completions: AP-ISR applied entries plus synchronous SBI
   RFENCE calls".
2. `smp.cpp` — defines `note_shootdown_applied()` as a single
   `__atomic_fetch_add(&shoot_applied_, 1ULL, __ATOMIC_RELAXED)`,
   byte-identical pattern to the adjacent `note_shootdown_send_failure()`.
3. `smp_shootdown.cpp` — on the RFENCE fast path
   (`sbi_call4(RFENCE, SFENCE_VMA, …)` with `ret.error == 0U`), calls
   `kernel::smp::note_shootdown_applied()` before the existing `return`.

`test-history.txt` and `prompts/LEARNINGS.md` churn in the same diff is
intentionally out of scope (observability metadata, not shipped code).

## 2. Root-cause plausibility (static, no re-execution)

The issue title ("IPI never lands") is disproven by the structure of the
code under audit, consistent with the developer's GDB note
(1× SSWI bring-up loopback, 0× `apply_shootdowns`, 0× send-failure):

- `VMM::smp_tlb_shootdown_hook` tries RFENCE **first** (`rfence_usable()`);
  on `error == 0` it `return`s — the mailbox/`apply_shootdowns` path is
  never entered by design. `shoot_applied_` was previously incremented
  **only** in `apply_shootdowns()` (3 sites: empty-slot full fence,
  corrupt-count fence, per-entry loop). A successful synchronous RFENCE
  therefore completed the invalidation while advancing no counter.
- The failing asserts (`test_tlb_shootdown.cpp:419,596` —
  `applied_counter_now() > applied_before` after a bounded poll) observe
  the counter, not the mapping. The functional asserts in the same tests
  (worker `TERMINATED`, `exit_code != SWEEP_EXIT_OK` after unmap/teardown,
  `:430-433, :509-510`) are the true delivery proofs — the report that
  they passed throughout is structurally credible: RFENCE success means
  the remote fence happened; only the test-visible counter lagged.
- Fix direction is therefore correct: account the fast path, don't
  re-plumb delivery. No delivery-path instruction is altered.

## 3. Safety checks (requested (a)–(e))

### (a) The increment cannot mask a REAL delivery failure — PASS

- **SBI contract:** `smp_shootdown.cpp:27-29` documents the RFENCE ecall
  as synchronous-block ("returns only after remote harts fence"), citing
  SBI RFENCE §8.2 / v3.0 §8.1.2 FID 1 `remote_sfence_vma`. This matches
  the published SBI semantics (RFENCE is a synchronous broadcast; `error`
  reports acceptance/completion, not fire-and-forget). Counting
  `error == 0` as a completed remote fence is the same equivalence the
  aarch64 lane already ships: `kernel.cpp:1400-1404` counts an SGI-receipt
  `tlb_flush_all()` via `note_shootdown_applied()` as an applied entry.
- **Error path untouched:** `ret.error != 0` still calls
  `note_shootdown_send_failure()` and falls through to the mailbox path
  (`:173-198`); `mask == ~0ULL` (unmapped hart) likewise falls through.
  A refused/failed RFENCE never takes the new increment.
- **Counter is observability-only, never a delivery gate:** the only
  production writer is the new call site + the 3 `apply_shootdowns`
  sites; the only reader of `shootdown_applied()` is the test helper
  `applied_counter_now()` (`test_tlb_shootdown.cpp:160-166`), consumed
  exclusively by bounded test polls (`:411-421`, `:588-598`) and the
  negative-control flatness check (`:520-523`). No kernel control flow
  (scheduler, VMM, teardown, IRQ) branches on the counter. Over-counting
  risk is bounded to test polling; under the SBI sync contract there is
  no over-count on the success leg (one RFENCE call ⇒ one increment,
  same cardinality as one applied batch entry).
- **Negative control preserved:** the no-hook test (`:520-523`) asserts
  the counter stays flat when no hook fires — the fix adds no increment
  outside the RFENCE-success leg, so that discrimination is intact.

### (b) No locks / alloc / IRQs — PASS

- New function body is one `__atomic_fetch_add … RELAXED` on the existing
  `shoot_applied_` word — identical to its mirror
  `note_shootdown_send_failure()` and to aarch64's
  `note_shootdown_applied()` (`aarch64/smp.cpp:190-192`).
- Call site is straight-line in the hook's RFENCE-success branch (any-task
  context per the file contract `:35`); no guard, no allocation, no IPI,
  no CSR access, no `ENSURE`/panic. Concurrency discipline
  (CODING_STYLE §11.6, all-or-nothing atomics) holds: every access to
  `shoot_applied_` is via `__atomic_*` (3 fetch_adds + ACQUIRE load
  reader); the new writer uses the same ordering as the existing writers.

### (c) Doc-contract change is accurate — PASS

- Old doc ("entries applied by AP ISR runs") was false the moment the
  RFENCE fast path shipped (#389): completions without ISR runs existed
  but were uncounted. New doc ("remote-fence completions: AP-ISR applied
  entries plus synchronous SBI RFENCE calls") describes exactly what the
  counter now accumulates, with the synchronicity rationale stated at
  both the declaration and the call site. `shootdown_send_failures()` doc
  ("never gates control flow") is unchanged and now symmetrically true of
  the applied counter via the new `note_shootdown_applied()` doc
  ("Monotonic, never gates control flow"). Doxygen shape (`@brief`/
  `@return`) and comment line lengths conform to CODING_STYLE §§8–9.

### (d) No x86 / aarch64 behavior change — PASS

- Diff touches 3 riscv64-only TUs (`arch/riscv64/hal/smp.{hpp,cpp}`,
  `arch/riscv64/hal/smp_shootdown.cpp`). No shared header, no VMM
  choke, no test TU, no `kernel.cpp` change. aarch64 already owns an
  identical `note_shootdown_applied()` (called from its SGI handler);
  x86 observes via `ShootdownBatch::applied_for_test()`. The change is
  parity-**restoring** (rv64 RFENCE leg now counts like the aa64 SGI leg),
  not parity-breaking — no cross-arch rule (CODING_STYLE §1 / AGENTS.md)
  violation.

### (e) Failure fall-through unchanged — PASS

- Verified hunk-by-hunk: the added 6 lines (comment + call) sit strictly
  inside `if (ret.error == 0U) { … return; }`. The
  `note_shootdown_send_failure();` line, the `mask == ~0ULL` guard, and
  the full mailbox loop (`request_full_fence` / `queue+flush` per CPU)
  are byte-identical to the parent. A present-but-failing RFENCE still
  reports failure **and** delivers via mailbox — never a silent drop.
