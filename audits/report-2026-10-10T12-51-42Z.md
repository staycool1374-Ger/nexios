## ANSWERS TO THE RAISED QUESTIONS

1. Reorder safety. The `TestContext` is a `test.cpp` static and is NOT captured
   by `snapshot_create` (the snapshot covers PMM/MemPool/TCB/ready-queue/PMML4/
   kslot/VMM PDs — not scheduler BSS), so moving the flag write does not change
   captured bytes. Enumerated `is_test_active()` consumers: on_tick monitor-wake
   (~3158), reap_orphans (~3629), balancer (~3651), harness-nonpreempt
   (~4679/4781), canary latches (scheduler.cpp:203, syscall.cpp:73), VMM touch
   flags (vmm.cpp:274/307), task stack alloc (task.cpp:1076), user-task-end
   suppression (kernel.cpp:1937), console routing (logger.cpp:52/72). All are
   either the intended fix or benign — but three are unadvertised (S3 above).
2. Right fix vs workaround. It reuses the existing, documented lifecycle
   mechanism (`harness_owns_lifecycle()` ⇒ `is_test_active()`), extending the
   "harness owns lifecycle" interval to cover the whole pre-suite window. That
   is semantically consistent (the harness is setting the suite up) and does
   not regress the monitor (the monitor is *already* not woken during the
   suite by design). It is not an assertion mask. Caveat (S3): the issue's own
   2026-10-10T11:54 comment diagnosed a different mechanism ("the tick
   dispatcher never switches away from the self-blocked monitor", explicitly
   "NOT monitor starvation"). The added `switch_to_task` counter (+10000 over
   10000 ticks) shows the dispatcher IS switching repeatedly, which supports
   the patch's starvation account and supersedes that comment — reconcile the
   issue thread.
3. Beacon. CONFIG_DEBUG-only: yes, both counters (`g_diag_*`) and the dump are
   inside `#if defined(CONFIG_DEBUG)`; no release residue. Firing gate on
   `task.id == 1` at 100/200/400 is correct. ISR/task context: `Logger` here
   is lock-free (`raw_write`/`print_dec` → `putchar`/`puts`), so no lock
   reentrancy hazard; under monitor=1 it runs in monitor task context holding
   `scheduler_lock_`. `diag_ready_probe`'s read is under that lock (S3: make
   the contract explicit). Recommendation: TRIM (keep a compact counters line;
   drop the full per-task dump + probe) before final.
4. #300. INDEPENDENT. #300 is a dead-tick wedge (synchronous `on_tick` /
   `handle_interrupt_c` from a task-context caller); if ticks are dead the
   monitor is never scheduled and this beacon never fires, and the starvation
   fix cannot help. No shared mechanism.
5. Regressions / non-x86 / quiescence. The earlier activation changes
   `arm_test_touch_flags` arming (S3 #1) and `in_test_harness` stack path (S3
   #2); both are arch-neutral in the gated code and the riscv64 path already
   opts out of the guard block. Snapshot quiescence (#321) is unaffected (the
   reorder does not touch inbox draining; the IPC-quiescent baseline is still
   produced by the boot settle). Four regression classes (storage/ipc/servers/
   capability) were single-attempt green, and all run snapshot_restore per
   test, so the changed restore path is exercised.
6. test-history.txt. The four regression rows look like genuine single runs
   (storage 162 / ipc 86 / servers 62 / capability 148 match established
   counts). The `logging_debug` row is annotated and self-described as
   non-native → S3 schema/honesty note.
