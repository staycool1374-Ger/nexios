## Findings A: IPC call path, fastpath, context-switch cost, scheduling donation

**IPC-1 [S1, confirmed by code read] Every blocking IPC hop costs up to one timer tick.**
- `reschedule()` only publishes a deferred switch pair; the switch is applied in the next timer-ISR epilogue (docs/specs/ipc.md §4 lines 109-113; scheduler.md §3.2 line 131 "one tick of lag").
- `Scheduler::set_task_ready` (src/kernel/task/scheduler_registry.cpp:424-436) enqueues the woken task without requesting a reschedule.
- `CONFIG_TICK_HZ 1000` (nexios_config.h:71) gives 1 ms per hop. A round trip App -> VFS -> Disk -> VFS -> App (parent #512, item 1) is at least 4 blocking hops, so up to about 4 ms of pure tick latency before any work.
- The FAST path (#11) removes copies only. docs/specs/ipc-fastpath.md §3.1 (lines 133-142) explicitly rejects a reduced context-switch cost as "not in scope".
- **Risk:** the spec §5 contract "IPC ≤10% vs in-kernel" (§9.4) cannot be met by the FAST path alone, and no per-hop latency bound exists.
- **Change needed:** state a normative per-hop wake-to-run bound in ipc.md §4, and either (a) request an immediate reschedule when a higher-priority passive server is woken, or (b) budget the tick latency in the WCET model. Hardware measurement is required: ipc-fastpath.md:442 says no absolute cycle bound is possible under TCG.

**IPC-2 [S1, confirmed by code read; runtime repro needed] Server death does not wake clients blocked in send_sync.**
- `send_sync` (src/kernel/ipc/ipc.cpp:485-579) blocks with `reply_wait=true` (lines 560-564).
- The only wake is a message arrival (ipc.cpp:350-365). The dest-death check (lines 540-558) runs only after a wake.
- Teardown (src/kernel/task/task.cpp:2663-2692) unlinks the dying task from its *own* blocked-senders list. It does not wake peers waiting for a reply from it.
- By contrast, the pager path wakes clients on pager death (docs/specs/external-pager.md:311).
- **Consequence:** after a server crash, its clients hang forever. This breaks the supervisor/restart premise of #191/#193 and violates CODING_STYLE §11.3 and §12.3 ("wakers own the wakeup contract") plus microkernel-transition.md §6(d).
- **Change needed:** on server teardown, drain reply waiters and error-reply them (for example `DEAD_SERVER`). Add a `death_drain` test (spec §8, #50). Validation: kill a server while a client is in send_sync; expected result today is a hang.

**IPC-3 [S2] Reply matching has no reply identity.**
- `send_sync` pops the oldest message from the sender id (ipc.cpp:503-506). Any non-reply from the same peer is consumed as the reply (LEARNINGS #296 already documents this).
- The donation chain in spec §5 needs a reply token or reply capability.
- **Change needed:** add a call id or reply cap to the Message header. Spec §5 must define it.

**IPC-4 [S2] Client-side wait is unbounded.**
- `send_sync` has no timeout. Only `send_sync_bounded` (ipc.cpp:582) is used, and only by proxies.
- An alive-but-stuck server blocks its clients forever. The MCS timeout fault (spec §1, §5) does not exist.
- **Change needed:** make a bound or timeout fault mandatory on every cross-server call (spec §5 normative).

**IPC-5 [S1 evidence, open issue #545] Shell queue lock wedge.** Issue #545 reports a sender spinning on the shell queue lock with (locked=1, holder=NULL) on x86. This is evidence that the message-queue lock discipline is not safe under current load. It must be closed before any server moves onto that path.

**SCHED-1 [S1, confirmed by code read] No scheduling-context donation exists; priority inversion is live today.**
- Grep for donation/SC/passive/reply-donation finds only mutex/semaphore PI (src/kernel/test/test_priority_inheritance.cpp). #190 is unimplemented, as the spec implies.
- vfsd and iocd are SPORADIC_SERVER at prio 20 with background priority 0 (src/kernel/task/taskdefs.cpp:301-305; SS(2,10,0)).
- `SporadicServer::current_priority()` returns `bg_priority_` (0) once EXHAUSTED (sporadic_server.hpp:151-154).
- **Inversion:** a client at priority P blocked on an exhausted vfsd waits behind every ready task with priority in (0, P). The wait is bounded only by the budget refill, not by the client deadline.
- **Change needed:** either SC donation (spec §5) or a PI boost of the server to the caller's priority on send. The mutex PI pattern (CODING_STYLE §11.5) is the reference.
- **Validation:** a 3-task test (low spinner, exhausted server, high client) asserting client latency ≤ a stated bound. Must be cross-arch (parity rule).

**SCHED-2 [S2] Budget granularity versus server latency.** SS(2,10,0) allows 2 ticks of service per 10 ticks. A request needing more than the remaining budget waits a full period (10 ms). Spec §5 "extra_refills" fragmentation bound is not implemented in the code I read. Confirm before relying on it.

**SCHED-3 [S3] Admission model.** `scheduler_admission.cpp` counts server budget as C (lines 118-135). The bound table is exact up to 20 tasks, then 0.693 (scheduler_admission_internal.hpp:15-16). Donated or passive budget is not modelled, so admission will under-count once passive servers exist. Also, briefing gotcha 11 says Liu-Leyland is "not enforced", but admission returns `SCHED_ERR_ADMISSION_DENIED` (scheduler_admission.cpp:135). Reconcile the doc or the code.
## Findings B: interrupt routing and userspace IRQ multiplexing

**IRQ-1 [S1, confirmed by code read; repro needed] No interrupt storm limiter on x86_64.**
- `IrqStormLimiter` is wired only in `aarch64/interrupt_controller.cpp:260` and `riscv64/interrupt_controller.cpp:148`. `CONFIG_IRQ_STORM_LIMIT 256` (nexios_config.h:123) has no x86 consumer.
- The default WAIT mode does not mask on delivery (irq_delivery.cpp:471-475; `mask_on_delivery` runs only for WAIT_ACK). x86 arms the IOAPIC level-triggered (irq_delivery.hpp:91-94).
- **Risk:** a stuck-asserted level line re-enters the ISR continuously. `++r->pending` is uncapped and the ring-0 loop starves the tick and every other task.
- **Change needed:** port the storm limiter to x86 (arch-parity rule) or mask-on-delivery for level-triggered WAIT lines. Validation: injected stuck-level line on all three arches; assert the tick keeps advancing.

**IRQ-2 [S2] Pending count is uncapped.** `uint32_t pending` (irq_delivery.hpp:105) is incremented without saturation (irq_delivery.cpp:473). A burst becomes a backlog that `sys_irq_wait` drains as N immediate returns, which starves the driver's own work. The doc's "never lost" holds only until 2^32, and it gives no latency bound. **Change:** cap the count and expose an explicit overflow/dropped counter to the driver.

**IRQ-3 [S2] NOTIFY mode coalesces silently.** NOTIFY delivery stores the last vector value (irq_delivery.cpp:488-498; irq_delivery.hpp:51-52), so per-interrupt counts are lost. A mux (#192) built on NOTIFY for high-rate lines loses events. **Change:** spec §4 must define counting semantics for the mux (a count word or per-IRQ counters).

**IRQ-4 [S2] Single waiter per slot is enforced only by recipient equality.** `r->waiter = t` (syscall_handlers_irq.cpp:237) overwrites silently. The guard is `r->recipient != t` (lines 212-214). That is sufficient for one recipient, but it breaks once one IRQ is shared among threads (#52 threads share an address space). **Change:** reject when `waiter != nullptr`.

**IRQ-5 [S2, implicit assumption, matches open #546] x86 slot lock is taken lock-only.** The comment at syscall_handlers_irq.cpp:186-200 says "x86 keeps lock-only (ISRs run with interrupts disabled)". Correctness depends on the x86 syscall entry running with IF=0. I did not inspect the IDT gate type, so this is unverified. **Validation:** confirm the syscall gate clears IF, then add a debug assert on the path.

**IRQ-6 [S2] IRQ-to-driver latency is one tick.** Same root cause as IPC-1: `set_task_ready` does not request a reschedule. Each mux hop adds up to 1 ms (CONFIG_TICK_HZ 1000). This is the latency risk named in parent #512, item 2.

**IRQ-7 [S3] Static IRQ capacity.** CONFIG_CAP_MAX_IRQ = 16 and CONFIG_CAP_MAX_MSIX = 8 (nexios_config.h:585, 594) bound the whole system to 24 IRQ sources. This must be budgeted for the static architecture (see the SDF table in Findings D).

**Reference: open issues on this path.** #546 (missing preemption/IRQ contract, S2) is the implicit-assumption umbrella for IRQ-5, IPC-1 and SCHED-1. #545 (S1) and #549 (lock-free ring enhancement, relevant to the SPSC bulk channels in spec §5) are on the same paths. #196 (latency cascades) overlaps IPC-1 and IRQ-6 and should be cross-referenced rather than duplicated.
## Findings C: kernel memory management (bootstrap, IPC allocation, fixed pools, recovery)

**MEM-1 [S2, confirmed by code read] Runtime PMM allocation exists on the IPC data path, which contradicts "kernel never allocates" (#193 premise, spec §2/§3).**
- `BufferPool::alloc_page` falls back to `PMM::alloc_user_page()` when the pool is empty (src/kernel/ipc/buffer_pool.cpp:220-242, line 242). The pool is backed by `CONFIG_BUFFER_POOL_PAGES 128` (nexios_config.h:250), but the handle table has `MAX_BUFFERS 1024` (buffer_pool.hpp:37). Between the 129th and the 1024th live buffer, each allocation hits the PMM at runtime.
- The return path can also push pages back to the PMM (buffer_pool.cpp:272-283).
- Other runtime PMM allocations: brk (src/kernel/syscall/syscall_handlers_misc.cpp:340) and the new-PML4 allocation on task creation (task.cpp:1988, path not yet traced).
- **Change needed:** remove the PMM fallback (return a typed `BUF_POOL_EXHAUSTED`) or size the pool to the maximum live buffer count, and add a static budget test.

**MEM-2 [S2] Fixed-pool exhaustion uses mixed policies.**
- Error returns: MemPool (cap objects, nullptr); BufferPool `BUF_INVALID_INDEX`; sync `SYNC_ERR_MAX_WAITERS` (32 waiters); IRQ claim -1.
- Blocking: IPC queue full blocks the sender (ipc.md).
- Fixed limits (nexios_config.h): MAX_TASKS 64 (line 58); IPC queue 16 msgs x 64 B (233, 222); CAP_MAX_UNTYPED 16 (571); CAP_MAX_DEATH_WATCHES 16 (731); CAP_MAX_PAGER_CLIENTS 8 (757); CAP_MAX_MMIO_MAPS 8; CAP_MAX_FRAME_MAPS 8; CAP_MAX_WDOG 8; CAP_MAX_IOMMU 16.
- **Risk:** the planned static architecture (about 10 servers, restart churn, 16 Untyped, 64 TCBs with zombie recycling before restart) has no written budget. Spec §6(e) requires OOM-as-error, which is not uniform.
- **Change needed:** one policy for exhaustion (spec §6(e)); a per-SDF worst-case object table for spec §4, checked by the `boot_composition` test.

**MEM-3 [S3] Dead configuration.** `CONFIG_HEAP_SIZE` (nexios_config.h:188-189, 16 MiB) is referenced nowhere under src/kernel. Decide whether to delete it or document it as the boot allocation budget. Do not remove it without owner confirmation.

**MEM-4 [S2] Recovery after a crash depends on IPC-2.** Restart cycles drain TCBs (zombie list, 0xDD poisoning under CONFIG_DEBUG). IRQ slots drain correctly (irq_delivery.cpp:595-644: recipient/waiter cleared, pending reset). IPC reply waiters are not drained, so a restarted server leaves its clients hung (IPC-2). Restart recovery is therefore blocked on IPC-2, not on memory.

**Bootstrap:** `BufferPool::init` pre-allocates 128 user pages with `ENSURE(phys != 0)` (buffer_pool.cpp:211). Failure at boot is a fatal panic, which is correct for an impossible-by-design condition. Document the boot memory budget next to it.

## New findings from the full spec pass (plus verification in code)

**DEATH-1 [S1, confirmed by spec + code read] Supervisor death notification is tied to idle-time cleanup.**
- death-notify.md: records latch only from `TaskControlBlock::cleanup()` (the "single death funnel"). In code, `cleanup()` calls `DeathNotify::on_task_death` (src/kernel/task/task.cpp:2743).
- zombie-list.md: `terminate()` only calls `release_zombie()`. `cleanup()` is reached from `IdleTask::cleanup_step()` (one TCB per idle pass, priority 0) or from `flush_zombies()`, which runs only when more than 32 zombies exist, checked every 100 ticks.
- idle_monitor.md Q2 confirms that under sustained load idle never runs.
- **Consequence:** under load, the supervisor learns of a server death only when idle runs again. The microkernel restart premise (#191/#193) is unbounded. Open #516 (fault kills bypass notify_death) is a related symptom of the same funnel.
- **Change needed:** notify from the death path (terminate or release_zombie), not only from cleanup. Define a supervisor-visible death latency bound. Test: kill a server under full CPU load; assert the record arrives within a stated bound.

**SCHED-1 (restated) [S1 for RT clients; S2 for the boost mechanics].**
- **S1:** there is no sched-context donation. The spec's priority convention (scheduler.md §0) puts vfsd/iocd at 20. Any RT client above 20 that calls them is inverted behind every ready task with priority between 20 and its own. The server runs at its base priority, and the boost in block_sender only applies when a send hits a full queue.
- **S2:** the existing boost is not transitive. If the owner is itself blocked on another queue, the boost does not propagate to that queue's owner. A chain A→B→C therefore loses the boost at the second hop.
- **Change needed:** the donation design (spec §5) or an explicit "no donation, enforced by deployment priority" rule with a check at SDF compose time. Either way, the transitive case needs a test.

**SCHED-4 [S2, spec-based; code not checked] The starvation breaker cannot promote level 0.**
- scheduler.md §3.3: the breaker forces a dispatch from the highest READY level below H, but level 0 is never a forced target.
- sporadic_server.hpp:151-154 drops an exhausted server to bg_priority (0 for vfsd/iocd per taskdefs.cpp:301-305).
- **Consequence:** an exhausted server runs only when no task at priority ≥1 is READY. Under the SS(2,10,0) model, that is 8 of every 10 ticks lost to other tasks when any ready task exists. Latency is bounded by replenishment, but the throughput loss is large.
- **Change needed:** choose a background priority above the breaker's floor, or let the breaker serve level 0 for exhausted servers. Validate with a constant-load client run.

**IPC-1 (reconfirmed):** every blocking hop is applied by the next timer ISR (ipc.md §4; scheduler.md §3.2). A round trip has at least four blocking hops, so about 4 ms of tick latency at 1 kHz before any work.

**IPC-2 (split):** plain `send_sync` callers still hang when the server dies [S1, runtime repro needed]. Proxies with `send_sync_bounded` return after up to 5000 ticks [S2, 5 s RT-unacceptable].

**IRQ-1 (reconfirmed, plus the spec basis):** irq-early-init.md §4 documents the storm limiter as landed for GIC and PLIC only. It does not mention x86. This confirms there is no x86 limiter.

**STATIC-1 [S2] IO-port grant budget.** configuration.md §1.11: `CONFIG_IOPB_MAX_TASKS = 4`. Port grants are per task. The current driver PDs already need four: serial (COM1), kbd (0x60–0x64), rtc (0x70–0x71), and block (0x1F0/0x170 for ATA). Any fifth PD with port caps fails closed. The static architecture (microkernel-transition §4) must budget this, or the bound must change.

**STATIC-2 [S2] DMA mapping budget.** configuration.md: `CONFIG_IOMMU_MAX_DOMAINS = 8`, `CONFIG_IOMMU_MAX_MAPPINGS = 32` per domain. A net driver PD with RX rings may exceed 32 mappings and fail closed. Size it from the SDF, not from defaults.

**WCET-1 [S2, TCG relative only] on_tick budget.** wcet-reaudit-v0.4.5.md: `scan_deadlines` worst case 2,030,000 cycles with 30 overrun tasks, measured under TCG. At 1 kHz that is about one full tick at 2 GHz. The scan runs under `scheduler_lock_` inside the timer ISR. The static architecture must be re-measured at its real task count, on hardware.

**MEM-5 [S2, unresolved] TCB size vs MemPool.** mempool.cpp:98-106 returns nullptr when no pool block fits (find_pool at 157-167). The largest block in configuration is 4096 B (nexios_config.h:304). admission_selftest.cpp:44 says `sizeof(TaskControlBlock)` is about 16 KiB, and the kernel boots. The two claims cannot both be true. The comment is probably stale, but it is unverified. **Change:** add `static_assert(sizeof(TaskControlBlock) <= max pool block)`.

**MEM-6 [S2] Budget vs BufferPool fallback.** oom-rt.md §2 charges PMM allocations to the per-task budget. The BufferPool fallback (buffer_pool.cpp:242) allocates from the PMM. Whether it is charged to a task budget is not stated in any spec or in the code I read. Confirm before the IPC data path moves to servers.

**DOC-1 (widened) [S2] Three sources disagree on #191 and #193.**
- microkernel-transition.md §2 and §8: #191 = memory manager, #193 = supervisor.
- driver-pds.md: "#193 supervises restarts".
- idle_monitor.md §3: "#191 restart" (this matches the issues).
- The issue titles: #191 = static system architecture + supervision, #193 = userspace frame/region manager.

**DOC-7 [S3] MemPool numbers.** memory.md §1 says "pool-2 = 64-byte blocks, 320 blocks". configuration.md and nexios_config.h give 64 blocks for the 64-byte class. memory.md §4 uses 320 as a bitmap bound, not as the count. The spec should say so.

**Positive finding (bulk path):** shm.md already provides a zero-copy SPSC ring with capability-gated mapping and a revocation closure, and no syscall on the data path. The serial and console PDs run on it. Spec §5 "SPSC bulk channels" is partly built. Open #549 is the lock-free enhancement.

2. SCHED-1 and SCHED-4: donation or enforced deployment priority, plus the breaker floor for level 0.
3. IRQ-1: x86 storm limiter (or mask-on-delivery for level WAIT lines). Cross-arch.
4. MEM-1 and MEM-5: remove the PMM fallback from the IPC data path; add the TCB static_assert.
5. STATIC-1, STATIC-2, WCET-1: budget the static architecture (IO-port tasks, DMA mappings, on_tick scan) before it is frozen.
6. IRQ-2, IRQ-3, IRQ-4: pending cap, NOTIFY counting, single-waiter assert.
7. DOC-1, DOC-2, DOC-3, DOC-5, DOC-6, DOC-7: fix the spec and issue references.

### Judgement
1. **DEATH-1 and IPC-2 are the two blockers.** Restart cannot be credible until a server death notifies supervisors on the death path, and until plain send_sync clients are woken on server death. Both are S1.
2. **IPC-1 is the architectural limit.** Each hop costs up to one tick (1 ms at 1 kHz), and the current design gives no way around it short of an immediate reschedule. This decides whether the target latency is reachable at all; it needs an owner decision before the protocol is frozen.
3. **SCHED-1 + SCHED-1b:** donation is missing and the existing boost is local only. Either build donation or enforce, at SDF compose time, that no client may outrank the server it calls. Pick one.
4. **MEM-1 and MEM-6 together** mean the IPC data path is neither bounded nor budgeted. Fix before any data path moves to a server.
5. **REFUTED:** IRQ-5 as a defect. Keep as documentation.
6. **Stale documentation to correct now:** nexios_config.h MemPool/TCB comment, the dead CONFIG_MEMPOOL_* macros, CONFIG_CAP_MAX_CNODES in cspace.md, the briefing's "Liu-Leyland not enforced" line, and the #191/#193 mapping.
